title: "LangChain and LangGraph"
description: "Record every run of a LangChain or LangGraph agent for one case, with its decisions and approvals, in TypeScript or Python"
---

This page shows how to add the Sanning adapter to a LangChain or LangGraph agent, so that each run records its steps, decisions and approvals for one case. You end with records in the console. Sanning stamps them on the public record at the end of the interval.

<Note>
  To test, use a Sandbox API key, and see [Test in the Sandbox](/sandbox).
</Note>

Before you start, do the [Quickstart](/quickstart): you need a Live API key and a seed for your agent's signing key, both in environment variables. The API key from the Quickstart already has the scopes the adapter needs (`agent:enroll` and `anchor:write`) and the scope that `bundle` needs later (`anchor:read`).

The example agent on this page has no model, so you need no key from a model provider. It has three nodes: one asks for a tool call, one runs the tool, and one pauses for a person to approve. To use your own agent, keep the Sanning parts and replace the graph.

<Steps>
  <Step title="Install the adapter">
    <CodeGroup>

    ```bash TypeScript
    npm install @sanning/anchor @sanning/anchor-langchain @langchain/core @langchain/langgraph zod
    ```

    ```bash Python
    pip install "sanning-anchor[langchain]" langgraph
    ```

    </CodeGroup>

    In TypeScript, the adapter is its own package and takes `@langchain/core` as a peer dependency. In Python, the adapter ships inside `sanning-anchor`, and the extra pulls in LangChain.
  </Step>

  <Step title="Start with an agent">
    The following graph makes one tool call that states a decision, and then pauses for approval. The tool, `record_conclusion`, is how the agent states its decision, and the `review` node is where a person approves.

    <CodeGroup>

    ```ts TypeScript
    import { AIMessage } from "@langchain/core/messages";
    import { tool } from "@langchain/core/tools";
    import {
      Command,
      END,
      interrupt,
      MemorySaver,
      MessagesAnnotation,
      START,
      StateGraph,
    } from "@langchain/langgraph";
    import { ToolNode } from "@langchain/langgraph/prebuilt";
    import { z } from "zod";

    const recordConclusion = tool(async ({ verdict }) => verdict, {
      name: "record_conclusion",
      description: "State the verdict for the claim.",
      schema: z.object({ verdict: z.enum(["approved", "declined"]) }),
    });

    const graph = new StateGraph(MessagesAnnotation)
      .addNode("assess", () => ({
        messages: [
          new AIMessage({
            content: "",
            tool_calls: [
              { id: "call_1", name: "record_conclusion", args: { verdict: "declined" } },
            ],
          }),
        ],
      }))
      .addNode("tools", new ToolNode([recordConclusion]))
      .addNode("review", () => {
        const answer = interrupt({ question: "Confirm the declined verdict?" });
        return { messages: [new AIMessage(`Reviewer answered: ${JSON.stringify(answer)}`)] };
      })
      .addEdge(START, "assess")
      .addEdge("assess", "tools")
      .addEdge("tools", "review")
      .addEdge("review", END)
      .compile({ checkpointer: new MemorySaver() });
    ```

    ```python Python
    from langchain_core.messages import AIMessage
    from langchain_core.tools import tool
    from langgraph.checkpoint.memory import MemorySaver
    from langgraph.graph import END, START, MessagesState, StateGraph
    from langgraph.prebuilt import ToolNode
    from langgraph.types import Command, interrupt


    @tool
    def record_conclusion(verdict: str) -> str:
        """State the verdict for the claim."""
        return verdict


    def assess(state):
        call = {"id": "call_1", "name": "record_conclusion", "args": {"verdict": "declined"}}
        return {"messages": [AIMessage(content="", tool_calls=[call])]}


    def review(state):
        answer = interrupt({"question": "Confirm the declined verdict?"})
        return {"messages": [AIMessage(content=f"Reviewer answered: {answer}")]}


    graph = (
        StateGraph(MessagesState)
        .add_node("assess", assess)
        .add_node("tools", ToolNode([record_conclusion]))
        .add_node("review", review)
        .add_edge(START, "assess")
        .add_edge("assess", "tools")
        .add_edge("tools", "review")
        .add_edge("review", END)
        .compile(checkpointer=MemorySaver())
    )
    ```

    </CodeGroup>
  </Step>

  <Step title="Add the adapter, with a case ID">
    Make an anchorer, which signs your records and sends them to Sanning, and make the handler that you pass to LangChain as a callback.

    The case ID is the matter that the work is for. Give it to the handler, and every record of the run carries it, so that you can build one evidence pack for the whole case later. Each record carries its case ID permanently, and nobody can change or withdraw it. The ID reaches Sanning as plain text. Use an ID that means nothing outside your systems: no names, no paths, no personal data. If you need to find a case by customer, keep that link in your own systems.

    <CodeGroup>

    ```ts TypeScript
    import { createAnchorer, LocalEd25519Signer, ObjectLogStore } from "@sanning/anchor";
    import { S3ObjectStore } from "@sanning/anchor/s3";
    import { anchorCallbacks } from "@sanning/anchor-langchain";
    import { S3Client } from "@aws-sdk/client-s3";

    const logStore = new ObjectLogStore(
      new S3ObjectStore({
        bucket: process.env.SANNING_LOG_BUCKET!,
        client: new S3Client({}),
      }),
    );

    const anchorer = createAnchorer({
      signer: LocalEd25519Signer.fromSeedHex(process.env.SANNING_SIGNING_SEED!),
      subject: { type: "agent", agent_id: "claims-triage" },
      apiKey: process.env.SANNING_API_KEY!,
      logStore,
    });

    const caseId = "case-4b19de";
    const evidence = anchorCallbacks(anchorer, { caseId });
    ```

    ```python Python
    import os

    from sanning_anchor import (
        Anchorer,
        AnchorCallbackHandler,
        LocalEd25519Signer,
        ObjectLogStore,
    )
    from sanning_anchor.s3 import S3ObjectStore

    log_store = ObjectLogStore(
        S3ObjectStore(
            bucket=os.environ["SANNING_LOG_BUCKET"],
            region=os.environ["AWS_REGION"],
        )
    )

    anchorer = Anchorer(
        signer=LocalEd25519Signer.from_seed_hex(os.environ["SANNING_SIGNING_SEED"]),
        subject={"type": "agent", "agent_id": "claims-triage"},
        api_key=os.environ["SANNING_API_KEY"],
        log_store=log_store,
    )

    case_id = "case-4b19de"
    handler = AnchorCallbackHandler(anchorer, case_id=case_id)
    ```

    </CodeGroup>

    Replace `claims-triage` with the agent ID, the name that identifies your agent to Sanning, and keep it stable: it is how the agent shows on the **Agents** page. Replace `case-4b19de` with the ID of the case from your own system. A case ID is 1 to 128 characters of letters, digits, `_`, `.`, `:` and `-`.

    The anchorer and the log store are the ones you set up in the Quickstart: see [Set up your log store](/quickstart#set-up-your-log-store) and [Create the anchorer](/quickstart#create-the-anchorer). The log store keeps the content of each step in your S3 bucket, and Sanning never receives it. With a Live API key, every record needs a log store. For why you keep the content, see [Keep your content](/evidence/build#keep-your-content).

    The mode (Sandbox or Live) comes from the start of your API key, so you set nothing else.
  </Step>

  <Step title="Record decisions from a named tool">
    A framework records tool calls, and it cannot tell which call is a decision. Put each decision in a tool, and name that tool to the adapter. When the tool ends without an error, the adapter writes a Decision record with the name that you give it. The value is what the tool returned, and it is hashed with the record like any other content.

    Name the decision for what was decided, and put the outcome in the value. The name `claim_verdict` with the value `declined` is right. The name `claim_declined` is not: a name that holds one outcome stops a reviewer from comparing decisions.

    <CodeGroup>

    ```ts TypeScript
    const evidence = anchorCallbacks(anchorer, {
      caseId,
      decisions: [{ tool: recordConclusion, name: "claim_verdict" }],
    });
    ```

    ```python Python
    from sanning_anchor import DecisionTool

    handler = AnchorCallbackHandler(
        anchorer,
        case_id=case_id,
        decisions=[DecisionTool(record_conclusion, "claim_verdict")],
    )
    ```

    </CodeGroup>

    Pass the tool object. The handler refuses a tool that does not exist, a tool named twice, and a name that is not a valid label (1 to 128 characters, with no control characters), when you construct it. A call that ends with an error writes no decision.
  </Step>

  <Step title="Record approvals">
    When a person must approve a step, use a LangGraph `interrupt()`, as the `review` node does. An interrupt does not say who decides, so tell the adapter, and tell it how to read the answer. The adapter then writes an Approval requested record when the node pauses, and an Approval resolved record when the run resumes.

    <CodeGroup>

    ```ts TypeScript
    const evidence = anchorCallbacks(anchorer, {
      caseId,
      decisions: [{ tool: recordConclusion, name: "claim_verdict" }],
      approvals: {
        actor: "human",
        // The value that resumes the run is the answer.
        verdict: (resume) =>
          (resume as { approved?: boolean }).approved ? "approved" : "rejected",
      },
    });
    ```

    ```python Python
    from sanning_anchor import ApprovalOptions

    handler = AnchorCallbackHandler(
        anchorer,
        case_id=case_id,
        decisions=[DecisionTool(record_conclusion, "claim_verdict")],
        approvals=ApprovalOptions(
            actor="human",
            # The value that resumes the run is the answer.
            verdict=lambda resume: "approved" if resume.get("approved") else "rejected",
        ),
    )
    ```

    </CodeGroup>

    `actor` is `human`, `policy` or `model`. `verdict` returns `approved`, `rejected` or `edited`, and it must raise an error for a value that is not an answer. Only a LangGraph resume command answers a pending approval.

    The two records are in different runs, and a LangGraph `thread_id` ties them together. A `thread_id` is 1 to 128 characters of letters, digits, `_`, `.`, `:` and `-`. Use an ID that means nothing outside your systems: the adapter refuses every record of a run whose `thread_id` is an email address, for example.

    The request waits in the process until the run resumes. If the answer can arrive in another process, pass a store that outlives the first process as `approvals.pending` (`pending` in Python). Without `approvals`, the adapter records no approvals, and the first record of each run says so.
  </Step>

  <Step title="Close the run, and check for gaps">
    A run with no closing record cannot show how it ended, and a reader cannot tell it from a process that died. The closing record holds the outcome you state and the outcome the adapter observed. If they differ, a reviewer sees both. You must close the run in every case.

    The closing record also lists the records that the run wrote. A step that could not be recorded is a gap, and `close()` reports it. Check for gaps when you close, because the agent keeps running by default when a record is lost.

    <CodeGroup>

    ```ts TypeScript
    import { awaitAllCallbacks } from "@langchain/core/callbacks/promises";

    const config = {
      configurable: { thread_id: "claim-4471" },
      callbacks: [evidence],
    };

    try {
      // The first call pauses at the review node. The second is the answer.
      await graph.invoke({ messages: [] }, config);
      await graph.invoke(new Command({ resume: { approved: true } }), config);
    } catch (error) {
      await awaitAllCallbacks();
      await evidence.close({ outcome: "failed", reason: "error" });
      throw error;
    }

    // LangChain.js can run callbacks in the background. Wait for them, or the
    // closing record is written without the last step.
    await awaitAllCallbacks();
    await evidence.close({ outcome: "completed" });
    if (!evidence.isComplete) {
      console.error("Records are missing from the trail:", evidence.gaps, evidence.unbuilt);
      process.exitCode = 1;
    }

    // The handler never closes the anchorer. Close it when the process is done.
    await anchorer.close({ raiseOnGaps: false });
    if (evidence.isComplete) {
      console.log(`Recorded case ${caseId}.`);
    }
    ```

    ```python Python
    config = {"configurable": {"thread_id": "claim-4471"}, "callbacks": [handler]}

    try:
        # The first call pauses at the review node. The second is the answer.
        graph.invoke({"messages": []}, config)
        graph.invoke(Command(resume={"approved": True}), config)
    except BaseException:
        handler.close(raise_on_gaps=False, outcome="failed", reason="error")
        raise

    # Raises IncompleteTrailError if any record is missing from the trail.
    handler.close(outcome="completed")

    # The handler never closes the anchorer. Close it when the process is done.
    anchorer.close()
    print(f"Recorded case {case_id}.")
    ```

    </CodeGroup>

    `outcome` is `completed`, `failed`, `interrupted` or `unknown`. `reason` is a code: `error`, `timeout`, `cancelled`, `interrupted` or `policy`. State the outcome on the first `close()`: a later one does not rewrite the closing records.
  </Step>

  <Step title="Run it, and see the records">
    Put the pieces in one file: `agent.mts` for TypeScript or `agent.py` for Python. The [whole file](#the-whole-file) is at the end of this page. Check that `SANNING_API_KEY`, `SANNING_SIGNING_SEED` and `SANNING_LOG_BUCKET` are set, then run it.

    <CodeGroup>

    ```bash TypeScript
    npx tsx agent.mts
    ```

    ```bash Python
    python agent.py
    ```

    </CodeGroup>

    {/* OUTPUT FROM REAL RUN: the last line the script prints, "Recorded case case-4b19de.", and nothing else when the trail is complete */}

    Open the [console](https://console.sanning.io) and go to **Records**. Each row is a record from your run: the run starts, the steps and the tool call run, the decision is stated, and the approval is requested and then resolved. The run ends with a closing record. The columns are Received, Agent, Kind and Signed by. A **Witness** strip at the top of the table shows the block time of the latest stamp, which is the time the public record confirmed it.

    The page does not mark each record as stamped. Sanning seals the records of each 10-minute interval, and the proofs are ready about a minute later. The public record can take longer to confirm a stamp, sometimes hours. To know whether your records are stamped, run `bundle`, as in [Build an evidence pack](/evidence/build#wait-for-the-stamp).
  </Step>
</Steps>

## If a step must not run unrecorded

By default, a lost record does not stop the agent. If a step must not run unless its record is kept, build the anchorer with `failClosed`. The handler then waits for each step's records and stops the agent when one is lost, before the next step runs. A tool whose start record is lost does not run.

<CodeGroup>

```ts TypeScript
const anchorer = createAnchorer({
  signer: LocalEd25519Signer.fromSeedHex(process.env.SANNING_SIGNING_SEED!),
  subject: { type: "agent", agent_id: "claims-triage" },
  apiKey: process.env.SANNING_API_KEY!,
  logStore,
  failClosed: true,
});
```

```python Python
anchorer = Anchorer(
    signer=LocalEd25519Signer.from_seed_hex(os.environ["SANNING_SIGNING_SEED"]),
    subject={"type": "agent", "agent_id": "claims-triage"},
    api_key=os.environ["SANNING_API_KEY"],
    log_store=log_store,
    fail_closed=True,
)
```

</CodeGroup>

After a handler stops the agent, it refuses every later step. Make one handler for each case, and share one anchorer between them.

## What the adapter cannot record

For example, the first record of each run lists approvals when you do not pass `approvals`, and decisions when you name no decision tool. The record types, and which LangChain event writes each, are in [Using adapters](/adapters#how-adapters-work).
