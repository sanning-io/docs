One callback handler records every step of a run: each chain step, model call, tool
call and retrieval, and every file that a tool produces. Each step becomes its own
signed record. You add the handler once, where your agent runs.

Before you start, do the [Quickstart](/quickstart): you need an API key, a signing
seed and the SDK.

## Install the adapter

<CodeGroup>

```bash TypeScript
npm install @sanning/anchor-langchain @sanning/anchor @langchain/core
```

```bash Python
pip install "sanning-anchor[langchain]"
```

</CodeGroup>

In TypeScript the adapter is its own package and takes `@langchain/core` as a peer
dependency. In Python the handler ships inside `sanning-anchor`, and the extra pulls
in LangChain.

## Record your first run

Make an anchorer, which signs and sends your records, and pass the handler the way
you pass any other LangChain callback. `agent` here is whatever you already invoke.

<CodeGroup>

```ts TypeScript
import {
  createAnchorer,
  FsLogStore,
  LocalEd25519Signer,
} from "@sanning/anchor";
import { anchorCallbacks } from "@sanning/anchor-langchain";
import { awaitAllCallbacks } from "@langchain/core/callbacks/promises";

const seedHex = process.env.SANNING_SIGNING_SEED;
const apiKey = process.env.SANNING_API_KEY;
if (!seedHex || !apiKey) {
  throw new Error("set SANNING_SIGNING_SEED and SANNING_API_KEY");
}

const anchorer = createAnchorer({
  signer: LocalEd25519Signer.fromSeedHex(seedHex),
  subject: { type: "agent", agent_id: "claims-triage" },
  apiKey,
  logStore: new FsLogStore("./logstore"),
});

const evidence = anchorCallbacks(anchorer);
try {
  await agent.invoke({ input: question }, { callbacks: [evidence] });
} finally {
  // LangChain JS can run callbacks in the background: wait for them,
  // then close the run, even when invoke throws.
  await awaitAllCallbacks();
  const { gaps } = await evidence.close();
}

// The handler never closes the anchorer. Close it when the process is done.
await anchorer.close();
```

```python Python
import os

from sanning_anchor import Anchorer, AnchorCallbackHandler, FsLogStore, LocalEd25519Signer

anchorer = Anchorer(
    signer=LocalEd25519Signer.from_seed_hex(os.environ["SANNING_SIGNING_SEED"]),
    subject={"type": "agent", "agent_id": "claims-triage"},
    api_key=os.environ["SANNING_API_KEY"],
    log_store=FsLogStore("./logstore"),
)

# Leaving the block closes the run, and checks that every step was recorded.
with AnchorCallbackHandler(anchorer) as handler:
    agent.invoke(inputs, config={"callbacks": [handler]})

# The handler never closes the anchorer. Close it when the process is done.
anchorer.close()
```

</CodeGroup>

Replace `claims-triage` with a name for this agent. Keep it stable: it is how the agent
shows on the **Agents** page.

The log store keeps the content of each step, on your own disk. Sanning never receives
it, and you build evidence packs from it. On a Live API key, every record needs a log
store: the SDK refuses to sign a record without one. For a store that outlives one
machine, see
[Keep the content](/guides/evidence#keep-the-content).

**Close every run.** In TypeScript, close in a `finally` block, so that a run that
throws still gets its closing record. In Python, use the `with` block. A run with no
closing record cannot show how it ended.

Next, wait a few minutes for the stamp, and then
[build and verify evidence](/guides/evidence) to see Verified.

## Record decisions

A framework sees tool calls, not decisions. So put each decision in a tool, and name
that tool to the handler. When the tool ends `completed`, the handler writes an
`agent.decision` record with the name that you give. Its value is what the tool
returned.

Name the decision for what is decided, and put the result in the value. Use the name
`credit_verdict` with the value `declined`. Do not use the name `credit_declined`: a
name that holds one result stops a reviewer from comparing decisions.

<CodeGroup>

```ts TypeScript
import { tool } from "@langchain/core/tools";
import { z } from "zod";
import { anchorCallbacks } from "@sanning/anchor-langchain";

// The tool your agent calls to state its conclusion.
const recordConclusion = tool(async ({ verdict }) => verdict, {
  name: "record_conclusion",
  description: "State the credit verdict for the application.",
  schema: z.object({ verdict: z.enum(["approved", "declined"]) }),
});

const evidence = anchorCallbacks(anchorer, {
  decisions: [{ tool: recordConclusion, name: "credit_verdict" }],
});
```

```python Python
from langchain_core.tools import tool
from sanning_anchor import AnchorCallbackHandler, DecisionTool


@tool
def record_conclusion(verdict: str) -> str:
    """State the credit verdict for the application."""
    return verdict


handler = AnchorCallbackHandler(
    anchorer, decisions=[DecisionTool(record_conclusion, "credit_verdict")]
)
```

</CodeGroup>

Pass the tool object. When you construct the handler, it refuses a tool that does not
exist, a tool named twice, and a name that is not a label. A call that ends `failed`
writes no decision.

## Record approvals

When a person must approve a step, use a LangGraph `interrupt()`. Tell the handler who
decides and how to read the answer. It then writes `agent.approval.requested` when the
node interrupts, and `agent.approval.resolved` when the run resumes.

<CodeGroup>

```ts TypeScript
const evidence = anchorCallbacks(anchorer, {
  approvals: {
    actor: "human",
    // Read the value that resumes the run as the answer.
    verdict: (resume) =>
      (resume as { approved?: boolean }).approved ? "approved" : "rejected",
  },
});
```

```python Python
from sanning_anchor import AnchorCallbackHandler, ApprovalOptions

handler = AnchorCallbackHandler(
    anchorer,
    approvals=ApprovalOptions(
        actor="human",
        # Read the value that resumes the run as the answer.
        verdict=lambda resume: "approved" if resume.get("approved") else "rejected",
    ),
)
```

</CodeGroup>

`actor` is `human`, `policy` or `model`. `verdict` returns `approved`, `rejected` or
`edited`, and it raises to refuse a value that is no answer. Only a LangGraph resume
command answers a pending approval.

The request waits in this process until the run resumes. When the resume can arrive in
another process, pass a store that outlives this one as `pending`. Without
`approvals`, the handler records no approvals, and the first record of each run says
so.

The handler records the paused step as `interrupted`, not `completed` or `failed`. When
the run resumes, LangGraph runs the tool again as a new tool call, with its own start
and end.

## Give each piece of work a case id

A case id joins the runs and the agents of one piece of work, such as one claim or one
application. Give it to the handler, and every record of the run carries it. Later you
build one evidence pack for the whole case.

<CodeGroup>

```ts TypeScript
const evidence = anchorCallbacks(anchorer, { caseId: "case-5d1e9a" });
```

```python Python
handler = AnchorCallbackHandler(anchorer, case_id="case-5d1e9a")
```

</CodeGroup>

A case id is 1 to 128 characters of letters, digits, `_`, `.`, `:` and `-`. It is
signed into each record, and it reaches Sanning in clear. So keep it opaque: no name,
no path, no customer data. If you need to find a case by a customer, keep that link in
your own systems.

## Hand work to another organization

When your agent sends work to an agent in another organization, each side records the
hand-off. The sender records what it sent, the receiver records what it received, and a
reviewer who holds both checks that they match. This works the same way with any
framework, over any transport.

<CodeGroup>

```ts TypeScript
import { createHandoff } from "@sanning/anchor";

// The sender. The case id groups every message in one case.
const handoff = createHandoff({ anchorer, caseId: "case-5d1e9a" });
const sent = await handoff.send({
  message: { task: "credit-assessment", recommendation: "approve", tier: 2 },
  to: RECEIVER_PUBLIC_KEY,
});
await transport.send({ body: sent.wireBytes, sanning: sent.attachment });

// The receiver, with its own anchorer, before its agent acts.
const received = await handoff.receive({
  attachment: arrived.sanning,
  wireBytes: arrived.body,
  outcome: "accepted",
  expectedSender: SENDER_PUBLIC_KEY,
});
```

```python Python
from sanning_anchor import create_handoff

# The sender. The case id groups every message in one case.
handoff = create_handoff(anchorer=anchorer, case_id="case-5d1e9a")
sent = handoff.send(
    message={"task": "credit-assessment", "recommendation": "approve", "tier": 2},
    to=RECEIVER_PUBLIC_KEY,
)
transport.send(body=sent.wire_bytes, sanning=sent.attachment)

# The receiver, with its own anchorer, before its agent acts.
received = handoff.receive(
    attachment=arrived["sanning"],
    wire_bytes=arrived["body"],
    outcome="accepted",
    expected_sender=SENDER_PUBLIC_KEY,
)
```

</CodeGroup>

Replace the following:

- `RECEIVER_PUBLIC_KEY` and `SENDER_PUBLIC_KEY` with each agent's Ed25519 public key,
  64 hex characters.
- `transport` with however your agents talk to each other.

`receive` checks the sender's record with the open-source verifier, in your process,
with no call to Sanning. Then it records what your agent did with the message:
`accepted`, `rejected` or `failed`. `expectedSender` refuses a sender that you did not
name, before anything is recorded.

## What the adapter records

Each callback commits the whole step: inputs, outputs, the serialized model, tags,
metadata, the run name and the tool call id. Nothing is edited before it is hashed.
Each callback writes one of the record types:

- Chain steps: `agent.step.started`, `agent.step.ended`.
- Model calls: `agent.model_call.started`, `agent.model_call.ended`.
- Tool calls: `agent.tool_call.started`, `agent.tool_call.ended`.
- Retrieval: `agent.retrieval.started`, `agent.retrieval.ended`.
- Files: `agent.file`.
- Decisions: `agent.decision`. Approvals: `agent.approval.requested` and
  `agent.approval.resolved`.
- Errors outside a step: `agent.error`.
- The start and the end of the run: `agent.run_opened` and `agent.run_closed`.

A step that fails is its `ended` record with `outcome.status` set to `failed`, not a
separate type. Model and tool facts, such as the provider and the model name, use the
names of the
[OpenTelemetry GenAI semantic conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/).
They are what the integration reported, not proof of what served the request. For
every field, see [Record types](/reference/record-types).

### What Sanning receives

The content is hashed in your process and stays with you. For each record, Sanning
receives the following, and nothing more:

| Sanning receives | Sanning never receives |
|---|---|
| The signed envelope of each record | Your signing key |
| The record type and its outcome | The content: prompts, outputs, tool input and output, files |
| The time the record was signed | A hash or a length of the content |
| The ids, in clear: agent, case, run, conversation and tool call | Names, such as the tool or the model |

Ids reach Sanning in clear, so keep names and personal data out of every id. Step and
tool names are signed into each record by default. A reviewer sees them, and Sanning
does not. To keep a name out of the record too, set `recordNames: false`
(`record_names=False` in Python).

## What the adapter cannot record

The first record of each run lists what the adapter cannot capture, in
`capture.not_captured`. For example, it lists approvals when you do not pass
`approvals`. A reviewer then knows what is missing, and that it is missing on
purpose.

## A missing step shows in the run

LangChain gives every step a `runId` and a `parentRunId`. The handler signs that
linkage into each record, with its own ordinal and a pointer to the previous record:

```json
"run": {
  "run_id": "01a08b4c-4479-715c-a63b-097b54be05ba",
  "parent_run_id": "01a08b4c-4475-750b-8a4f-2fd5e7775c4e",
  "root_run_id": "01a08b4c-4475-750b-8a4f-2fd5e7775c4e",
  "seq": 3,
  "prev_event_id": "1e70345c-879f-4c30-bf9a-c3e4797c3ff1"
}
```

Delete a record and the next one's pointer has nothing to point to. Reorder them and
`seq` disagrees. A reviewer can rebuild the run from the records alone, offline. The
verifier proves that an evidence pack is complete only against what the pack's signed
declaration says that it holds.

## Read the gaps

A step that cannot be recorded still takes its place in the run, so the records after
it cannot hide the hole. A gap is reported as undelivered, never as a bad record. Keep
each gap's record bytes: after a failure they are the only copy.

<CodeGroup>

```ts TypeScript
const { steps, gaps } = await evidence.close();
evidence.isComplete; // false if anything was dropped
```

```python Python
handler.gaps          # the outcomes that are not in the trail
handler.is_complete   # False if anything was dropped
```

</CodeGroup>

TypeScript's `close()` returns the gaps; pass `{ raiseOnGaps: true }` to make an
incomplete run an error. Python's `with` block raises `IncompleteTrailError` on a clean
exit with gaps. A block that is already unwinding logs its gaps, so the agent's own
exception survives.

The handler refuses to build a record whose id is not 1 to 128 characters of letters,
digits and `_ . : -`, such as a `thread_id` that is an email address. The refusal is a
gap, and by default the agent keeps running. `evidence.recordingStatus()`
(`handler.recording_status()` in Python) lists each refused record, with its type and
the field at fault, and never a value.

One anchorer can serve one handler per request. A handler counts only its own records,
so one request's lost record never marks another request incomplete. Close the
anchorer after every handler that uses it: that is where a record that is still
buffered is reported.

## Stop the agent when a record is lost

By default, recording never takes the agent down. Build the anchorer with
`failClosed: true` (`fail_closed=True` in Python) and the handler waits for each step's
records instead, and stops the agent when any record is lost, before the next step
runs. A tool whose start record is lost does not run.

A stopped handler stays stopped. Construct one handler for each run.

## Show which policy a step applied

To show which policy file a step read, have the tool that reads it return the file as
its artifact. The handler then writes an `agent.file` record on that step, and the
record commits to the file's own bytes.

<CodeGroup>

```ts TypeScript
const readPolicy = tool(
  async () => ["Loaded underwriting policy v3.", { path: "./policies/underwriting-v3.md" }],
  {
    name: "read_underwriting_policy",
    description: "Read the underwriting policy in force.",
    schema: z.object({}),
    responseFormat: "content_and_artifact",
  },
);
```

```python Python
@tool(response_format="content_and_artifact")
def read_underwriting_policy() -> tuple[str, dict]:
    """Read the underwriting policy in force."""
    return "Loaded underwriting policy v3.", {"path": "policies/underwriting-v3.md"}
```

</CodeGroup>

A reviewer who holds the policy runs `sha256sum` and compares the result with the
record's `event.content_hash`. The file's bytes go to your log store, and never to
Sanning. A tool that writes a file gets its own `agent.file` record in the same way,
with no setup.
