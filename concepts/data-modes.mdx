description: "What Sanning receives in Private, which ids it sees in clear, and how to hide or reveal a field"

The data mode decides what Sanning receives beside each signed record. Sanning offers
one mode: Private. The signed record and the evidence pack work the same way in every
mode, and a verifier reads every mode the same way. Each record states its mode in
`context.data_mode`, inside the signature.

One invocation has one mode. A verifier that holds two records of one invocation,
signed by one key, in two modes shows the finding `data_mode_mixed`.

## The three modes

The following table lists the three modes the vocabulary defines. Only Private is
offered.

| Mode | Sanning receives | Offered |
|---|---|---|
| Private | The signed envelope, record ids, times and outcomes. Every field is a fixed format: an id, a hash of a record, a timestamp, an integer or a closed list of words. | Yes |
| Standard | Private, plus names and counts. | Not offered yet |
| Full | Standard, plus hashes and lengths of content, file paths, and the content itself. | Not offered yet |

The vocabulary defines Standard and Full, and Sanning has switched them off. Use
Private.

## What Sanning receives in Private

Sanning receives no content and no hash of content. Sanning is content-blind in
Private, and it is never in the trust path: a verifier checks a pack offline with no call
to Sanning.

Sanning does receive ids in clear. These are the ids Sanning receives:

- the case id, `context.case_id`
- the run ids, in `run.run_id`, `run.parent_run_id` and `run.root_run_id`
- the chain key
- the conversation id
- the agent id

An id is 1 to 128 characters of `A-Z a-z 0-9 _ . : -`. Ids are never hashed, so
treat each one as public to Sanning. Keep a name, a path, a secret and customer content
out of every id.

When a case id would be personal data, use an opaque id instead, such as a random
string, and keep the link between that string and the person in your own systems. If
Sanning already stores an id you want gone, ask Sanning to clear it. Clearing stored ids
leaves the signed evidence untouched.

## Set the mode

The adapter and the record-builder write `context.data_mode` for you, as `private`. The anchorer has no mode setting, and the signed record is
the source for what Sanning receives: the SDK cuts what it sends to the mode the record
states.

## Hide and reveal a field

Two controls move one field across the line between clear and hash-only. Each is listed
inside the signed record, so a verifier can tell a withheld field from a missing one.
The fields a type can reveal or hide are listed in
[Event types](/reference/event-types#clear-fields-hash-only-fields-and-ids).

- **Reveal** a hash-only field to carry it in clear, for example tool arguments for an
  auditor. The field appears under its own name and its path is listed in
  `context.revealed`. Revealing a field changes the record you keep and hand to a
  verifier. In Private, Sanning does not receive it.
- **Hide** a clear field to withhold it, for example a tool name. The field is absent,
  and `context.hidden` maps its path to the SHA-256 of the JCS bytes of its value. The
  agent can disclose the value later, and a verifier confirms it against that hash.

A hidden field keeps the hash of its value. Anyone who holds a hidden field's hash and
guesses a short value, such as a tool name, can confirm the guess. Ids are never hidden.

## Credential scrubbing

An adapter can scrub the content object before it hashes it. The scrub walks the object
at every depth, and wherever a member's key contains `api_key`, `access_token`,
`authorization`, `bearer`, `secret`, `password` or `credential` (ASCII letters, any
case, with `_` or `-` optional in the first two), it replaces that member's whole value
with the string `"[scrubbed]"`. It matches keys only, never values, and renames nothing.

An adapter that scrubs writes `context.content_scrubbed: true`, whether or not it
replaced anything, because the hash then commits to the object after the scrub. A
verifier shows that fact. Hand-off messages and files are never scrubbed.

## Conversions and dates

The content object is what the framework handed the adapter. Where a value has no JSON
form, the adapter uses the framework's own JSON form of it. Where the framework has
none, these are the only conversions:

- An error is `{"message", "type"}`, with its class name as `type`.
- A date and time is an RFC 3339 UTC string with a four-digit year. A date and time with
  no UTC offset names no instant, and the adapter refuses it by name.
- A calendar date with no time is `YYYY-MM-DD`.
- Bytes are a base64 string.
- A number that is not finite is the string JavaScript prints for it.

Leaving out a member, renaming one or re-serializing the JSON changes the hash, so a
verifier holding the object can no longer confirm it.
