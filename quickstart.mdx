This guide shows you how to set up your agents for production. We'll be creating a Sanning API key, individual signing keys, and IDs, for your agents and a log store for your raw data.

## Pre-requisites

- Node.js 22 or later, or
- Python 3.11 or later

<Note>
  To test, use a Sandbox API key, and see [Test in the Sandbox](/sandbox).
</Note>

## Make a Live API key

An API key proves to Sanning which organization your agent records for. It never signs a record.

<Note>
  Sanning is in early access. To get an account, [book a call with us](https://calendar.google.com/calendar/u/0/appointments/schedules/AcZssZ18-Dhr-iEjRTlJFuFJNL9aTUjEu3pkzVx6VqyP3iRc_uZJd4hbdkog2KTmOml-hcmqhtGAqbfZ).
</Note>

1. Sign in to [console.sanning.io](https://console.sanning.io). If a strip across the top says Sandbox, select **Switch to live**.
2. Open **Settings**, then **API keys**, and select **Create key**. Only an owner or admin can create one.
3. Name the key and leave **Verify** unchecked: your agent only records and reads.
4. Copy the key. The console shows it once.

A Live API key starts with `sanning_prod_`.

The service that builds your evidence packs needs its own API key. Make it the same way, and tick **Hand-over**, the scope `handover:enroll`. An agent's API key never has this scope.

For more information, see [Build an evidence pack](/evidence/build#set-up-the-evidence-builder).

## Name your agent and generate its seed

Each agent needs an agent ID and a seed.

The agent ID is its name in Sanning, such as `claims-triage`. It shows on the **Agents** page and names the agent's folder in the log store. Keep it the same for the life of the agent.

The seed makes the agent's Ed25519 signing key. You can generate your agent's seed using the commands below.

<CodeGroup>

```bash OpenSSL
openssl rand -hex 32
```

```bash Python
python -c "import secrets; print(secrets.token_hex(32))"
```

```bash Node.js
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

</CodeGroup>

Two agents never share a seed or an agent ID.

The same command also generates the seed of the hand-over key to seal evidence packs. For more information, see [Build an evidence pack](/evidence/build#set-up-the-evidence-builder).

Sanning enrolls the signing key on your agent's first record via a cryptographic handshake.

To change the key later, rotate it: Sanning accepts a new key only when the old key signs the change. If a seed leaks, an owner or admin revokes the key in the console and re-keys the agent.

## Store them as environment variables

Put these values in the secret store that your service already uses. Each agent has its own agent ID and seed. The code in [Create the anchorer](#create-the-anchorer) reads them from these environment variables.

```bash
SANNING_AGENT_ID=AGENT_ID
SANNING_SIGNING_SEED=SEED
SANNING_API_KEY=API_KEY
```

Replace the following:

- `AGENT_ID`: the agent ID that you chose.
- `SEED`: the 64 hex characters that you made.
- `API_KEY`: the Live API key that you copied.

Never commit the seed or the API key to your code.

## Install the SDK

Install the SDK, this handles signing key enrollment, signing records and sending to Sanning and raw logs to a compatible S3 Object Storage.

<CodeGroup>

```bash TypeScript
npm install @sanning/anchor @aws-sdk/client-s3
```

```bash Python
pip install "sanning-anchor[s3]"
```

</CodeGroup>

## Set up your log store

Your log store is your own S3 bucket for the raw content of each record.

Sanning gets only hashes, so this raw content stays with you. When we Build an Evidence Pack later we'll read from this bucket.

Use one bucket for all your agents. Each agent writes to its own folder in it, named after its agent ID, so that each agent's content stays apart.

1. Choose a bucket name, and put it and its Region in environment variables:

   ```bash
    SANNING_LOG_BUCKET=BUCKET
    AWS_REGION=REGION
   ```

   Replace the following:

   - `BUCKET`: the name you choose for your bucket.
   - `REGION`: the AWS Region for the bucket, such as `eu-west-1`.

2. If the agent runs on AWS with a role, skip this step. Otherwise, set the storage keys as environment variables:

   ```bash
   AWS_ACCESS_KEY_ID=ACCESS_KEY_ID
   AWS_SECRET_ACCESS_KEY=SECRET_ACCESS_KEY
   ```

   Replace the following:

   - `ACCESS_KEY_ID`: the access key ID of your storage keys.
   - `SECRET_ACCESS_KEY`: the secret access key of your storage keys.

   The keys must be able to create, write to and read from the bucket. See the full list of required permissions [here](#the-exact-aws-permissions). Both SDKs look for keys the way AWS tools do: environment variables, then the shared config file, then an instance or task role.

   If no bucket exists, the SDK creates it with versioning and Object Lock in governance mode for 365 days. For that time, only a user who holds the AWS permission `s3:BypassGovernanceRetention` can delete or overwrite a stored version.

   If the bucket exists already, the SDK uses it and does not change it. It does not add Object Lock to a bucket that has none, so make a new bucket in that case.

<AccordionGroup>
  <Accordion title="The exact AWS permissions">
    Set these in AWS, on the keys or role that each service uses. Replace `BUCKET` with the name of your bucket.

    | | On `arn:aws:s3:::BUCKET` | On `arn:aws:s3:::BUCKET/*` |
    |---|---|---|
    | Agent | `s3:CreateBucket`, `s3:PutBucketVersioning`, `s3:PutBucketObjectLockConfiguration`, `s3:ListBucket`, `s3:GetBucketVersioning`, `s3:GetBucketObjectLockConfiguration` | `s3:PutObject`, `s3:GetObject` |
    | Evidence builder | `s3:ListBucket`, `s3:GetBucketVersioning`, `s3:GetBucketObjectLockConfiguration` | `s3:GetObject`, `s3:PutObject` |

    After the agent's first record, you can remove the first three from the agent. They only create the bucket. No service needs `s3:DeleteObject`.
  </Accordion>

  <Accordion title="Other S3-compatible stores">
    Sanning is built and tested for Amazon S3. Support for other storage providers is coming.

    The SDK might work with another service that has an S3-compatible API. Test it yourself before you rely on it. Set `SANNING_LOG_BUCKET` and `AWS_REGION` as in step 1, then set the service's address and keys:

    ```bash
    export AWS_ENDPOINT_URL_S3=ENDPOINT
    export AWS_ACCESS_KEY_ID=ACCESS_KEY_ID
    export AWS_SECRET_ACCESS_KEY=SECRET_ACCESS_KEY
    ```

    Replace the following:

    - `ENDPOINT`: the address of the service's S3 API, from its documentation.
    - `ACCESS_KEY_ID` and `SECRET_ACCESS_KEY`: the service's keys.

    If the service does not support Object Lock, the SDK warns and creates a plain bucket. The content is then not protected from deletion.

    Using another store? [Tell us which one](https://calendar.app.google/Znof4jp6fordTjhW6).
  </Accordion>
</AccordionGroup>

## Create the anchorer

The anchorer signs your records and sends them to Sanning. It needs your API key, your seed, an agent ID and your log store, with the agent's own folder in it. Every adapter uses this anchorer.

<CodeGroup>

```ts TypeScript
import {
  createAnchorer,
  LocalEd25519Signer,
  MemoryStore,
  ObjectLogStore,
} from "@sanning/anchor";
import { S3ObjectStore } from "@sanning/anchor/s3";

const agentId = process.env.SANNING_AGENT_ID!;

const logStore = new ObjectLogStore(
  new S3ObjectStore({
    bucket: process.env.SANNING_LOG_BUCKET!,
  }),
  { prefix: agentId },
);

const anchorer = createAnchorer({
  signer: LocalEd25519Signer.fromSeedHex(process.env.SANNING_SIGNING_SEED!),
  subject: { type: "agent", agent_id: agentId },
  apiKey: process.env.SANNING_API_KEY!,
  logStore,
  store: new MemoryStore(),
});
```

```python Python
import os

from sanning_anchor import (
    Anchorer,
    LocalEd25519Signer,
    MemoryStore,
    ObjectLogStore,
)
from sanning_anchor.s3 import S3ObjectStore

agent_id = os.environ["SANNING_AGENT_ID"]

log_store = ObjectLogStore(
    S3ObjectStore(
        bucket=os.environ["SANNING_LOG_BUCKET"],
    ),
    prefix=agent_id,
)

anchorer = Anchorer(
    signer=LocalEd25519Signer.from_seed_hex(os.environ["SANNING_SIGNING_SEED"]),
    subject={"type": "agent", "agent_id": agent_id},
    api_key=os.environ["SANNING_API_KEY"],
    log_store=log_store,
    store=MemoryStore(),
)
```

</CodeGroup>

Your code reads the `SANNING_` settings. The AWS library inside the SDK reads the `AWS_` settings, as every AWS tool does, so the samples need no Region or storage keys. The `store` line suits an adapter: each run starts its own chain of records, so nothing has to be kept after the agent stops.
