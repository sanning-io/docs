This page sets up what your agent needs to record for production: a Live API key, a seed for its signing key, the SDK (the package that signs records and sends them to Sanning), a log store, and an anchorer. Live is the mode that records real evidence. The Sandbox is the mode for testing. You need Node.js 22 or later, or Python 3.11 or later.

<Note>
  To test, use a Sandbox API key, and see [Test in the Sandbox](/sandbox).
</Note>

## Make a Live API key

An API key proves to Sanning which organization your agent records for. It never signs a record.

1. Sign in to [console.sanning.io](https://console.sanning.io). If a strip across the top says Sandbox, select **Switch to live**.
2. Open **Settings**, then **API keys**, and select **Create key**. Only an owner or admin can create one.
3. Name the key and leave **Verify** unchecked: your agent only records and reads.
4. Copy the key. The console shows it once.

A Live API key starts with `sanning_prod_`.

## Make a seed for the signing key

Your agent signs every record with its signing key, an Ed25519 key. You make the key from a 32-byte seed. You make the seed once. You keep it, and Sanning never receives it.

<CodeGroup>

```bash OpenSSL
openssl rand -hex 32
```

```bash Python
python -c "import secrets; print(secrets.token_hex(32))"
```

```bash Node.js
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

</CodeGroup>

Use one seed for each agent ID. To change it later, rotate the signing key: Sanning accepts a new key only when the old key signs the change. If a seed leaks, an owner or admin revokes the key in the console and re-keys the agent. Sanning enrolls the signing key on your agent's first record, so you do not register it anywhere.

## Store both as environment variables

Put the seed and the API key in the secret store that your service already uses. The adapter guides read them from `SANNING_SIGNING_SEED` and `SANNING_API_KEY`. To follow along from a terminal, export both:

```bash
export SANNING_SIGNING_SEED=SEED
export SANNING_API_KEY=API_KEY
```

Replace the following:

- `SEED` with the 64 hex characters that you made.
- `API_KEY` with the Live API key that you copied.

Never commit either value to your code.

<CodeGroup>

```bash TypeScript
npm install @sanning/anchor @aws-sdk/client-s3
```

```bash Python
pip install "sanning-anchor[s3]"
```

</CodeGroup>

In TypeScript, the second package is the AWS S3 library, which the Sanning SDK uses to reach your bucket but does not install for you.

In TypeScript, an adapter is a separate package. In Python, it ships inside `sanning-anchor`. Each adapter guide shows how to install its own.

## Set up your log store

A log store is your own S3 bucket for the content of each record. Sanning gets only hashes, so the content stays with you, and you need it to build an evidence pack. In Live, the SDK does not record without a log store.

1. Choose a bucket name, and put it and its Region in environment variables:

   ```bash
   export SANNING_LOG_BUCKET=BUCKET
   export AWS_REGION=REGION
   ```

   Replace the following:

   - `BUCKET`: the name you choose for your bucket.
   - `REGION`: the AWS Region for the bucket, such as `us-east-1`.

2. If the agent runs on AWS with a role, skip this step. Otherwise, set the storage keys as environment variables:

   ```bash
   export AWS_ACCESS_KEY_ID=ACCESS_KEY_ID
   export AWS_SECRET_ACCESS_KEY=SECRET_ACCESS_KEY
   ```

   Replace the following:

   - `ACCESS_KEY_ID`: the access key ID of your storage keys.
   - `SECRET_ACCESS_KEY`: the secret access key of your storage keys.

   The keys must be able to create and write to the bucket. For the list, see [The exact AWS permissions](#the-exact-aws-permissions). Both SDKs look for keys the way AWS tools do: environment variables, then the shared config file, then an instance or task role.

Without keys, the first record fails with a `RetentionError`, and nothing is sent to Sanning. The message ends with `Could not load credentials from any providers` in TypeScript and `NoCredentialsError: Unable to locate credentials` in Python. A direct `anchor` call throws the error. The LangChain adapter logs `step not anchored` for each step instead, and the agent keeps running with gaps in its trail.

On the agent's first record, the SDK creates the bucket with versioning and Object Lock in governance mode for 365 days. In that mode, nobody can delete or overwrite a stored version during that time unless they hold the AWS permission `s3:BypassGovernanceRetention`. A user who holds it can still remove a version. If the bucket exists already, the SDK uses it and does not change it.

<Note>
  The SDK can create the bucket only in `us-east-1`. For another Region, create the bucket before the agent's first record, as in [A bucket in another Region](#a-bucket-in-another-region).
</Note>

<AccordionGroup>
  <Accordion title="A bucket in another Region">
    With the AWS CLI, the first command creates the bucket with Object Lock, which also turns on versioning. The second sets the default retention:

    ```bash
    aws s3api create-bucket --bucket BUCKET --region REGION \
      --create-bucket-configuration LocationConstraint=REGION \
      --object-lock-enabled-for-bucket
    aws s3api put-object-lock-configuration --bucket BUCKET \
      --object-lock-configuration '{"ObjectLockEnabled":"Enabled","Rule":{"DefaultRetention":{"Mode":"GOVERNANCE","Days":365}}}'
    ```

    Replace the following:

    - `BUCKET`: the name of your bucket.
    - `REGION`: the AWS Region of the bucket, such as `eu-west-1`.
  </Accordion>

  <Accordion title="The exact AWS permissions">
    Replace `BUCKET` with the name of your bucket.

    For the agent that records, on `arn:aws:s3:::BUCKET`: `s3:CreateBucket`, `s3:PutBucketVersioning`, `s3:PutBucketObjectLockConfiguration`, `s3:ListBucket`, `s3:GetBucketVersioning` and `s3:GetBucketObjectLockConfiguration`. On `arn:aws:s3:::BUCKET/*`: `s3:PutObject`. The first three create the bucket. The three reads let the SDK check that the bucket exists and is protected. Without them, the SDK warns that it cannot check.

    After the agent's first record, you can remove `s3:CreateBucket`, `s3:PutBucketVersioning` and `s3:PutBucketObjectLockConfiguration` from its credential.

    No credential needs `s3:DeleteObject`.
  </Accordion>

  <Accordion title="Other S3-compatible stores">
    A service with an S3-compatible API, such as Cloudflare R2 or MinIO, works with the same samples. Set its address and its keys in environment variables. Both SDKs read `AWS_ENDPOINT_URL_S3`, so "Create the anchorer" does not change:

    ```bash
    export AWS_ENDPOINT_URL_S3=ENDPOINT
    export AWS_ACCESS_KEY_ID=ACCESS_KEY_ID
    export AWS_SECRET_ACCESS_KEY=SECRET_ACCESS_KEY
    ```

    Replace the following:

    - `ENDPOINT`: the address of the service's S3 API, from its documentation.
    - `ACCESS_KEY_ID` and `SECRET_ACCESS_KEY`: the service's keys.

    Set `SANNING_LOG_BUCKET` and `AWS_REGION` as in step 1. For `AWS_REGION`, use the Region name that the service documents.

    Many such services do not support Object Lock. The SDK then warns and creates a plain bucket, so the content is not protected from deletion.
  </Accordion>
</AccordionGroup>

## Create the anchorer

The anchorer signs your records and sends them to Sanning. It needs your API key, your seed, an agent ID and your log store. Every adapter uses this anchorer.

<CodeGroup>

```ts TypeScript
import { createAnchorer, LocalEd25519Signer, ObjectLogStore } from "@sanning/anchor";
import { S3ObjectStore } from "@sanning/anchor/s3";

const logStore = new ObjectLogStore(
  new S3ObjectStore({
    bucket: process.env.SANNING_LOG_BUCKET!,
    region: process.env.AWS_REGION!,
  }),
);

const anchorer = createAnchorer({
  signer: LocalEd25519Signer.fromSeedHex(process.env.SANNING_SIGNING_SEED!),
  subject: { type: "agent", agent_id: "claims-triage" },
  apiKey: process.env.SANNING_API_KEY!,
  logStore,
});
```

```python Python
import os

from sanning_anchor import Anchorer, LocalEd25519Signer, ObjectLogStore
from sanning_anchor.s3 import S3ObjectStore

log_store = ObjectLogStore(
    S3ObjectStore(
        bucket=os.environ["SANNING_LOG_BUCKET"],
        region=os.environ["AWS_REGION"],
    )
)

anchorer = Anchorer(
    signer=LocalEd25519Signer.from_seed_hex(os.environ["SANNING_SIGNING_SEED"]),
    subject={"type": "agent", "agent_id": "claims-triage"},
    api_key=os.environ["SANNING_API_KEY"],
    log_store=log_store,
)
```

</CodeGroup>

Both samples read the Region of the bucket from `AWS_REGION`. Replace `claims-triage` with the agent ID of your agent. Keep it stable: it is how the agent shows on the **Agents** page.
