Every step here is for Live, the mode that records real evidence. You need Node.js 22 or later, or Python 3.11 or later.

With several agents, each agent has its own seed, agent ID and folder, and all your agents use one log store. Repeat the steps that name a seed or an agent ID for each agent.

<Note>
  To test, use a Sandbox API key, and see [Test in the Sandbox](/sandbox).
</Note>

## Make a Live API key

An API key proves to Sanning which organization your agent records for. It never signs a record.

<Note>
  Sanning is in early access. To get an account, [book a call with us](https://calendar.google.com/calendar/u/0/appointments/schedules/AcZssZ18-Dhr-iEjRTlJFuFJNL9aTUjEu3pkzVx6VqyP3iRc_uZJd4hbdkog2KTmOml-hcmqhtGAqbfZ).
</Note>

1. Sign in to [console.sanning.io](https://console.sanning.io). If a strip across the top says Sandbox, select **Switch to live**.
2. Open **Settings**, then **API keys**, and select **Create key**. Only an owner or admin can create one.
3. Name the key and leave **Verify** unchecked: your agent only records and reads.
4. Copy the key. The console shows it once.

A Live API key starts with `sanning_prod_`.

The service that builds your evidence packs, the evidence builder, needs its own API key. Make it the same way, and tick **Hand-over**, the scope `handover:enroll`. An agent's API key never has this scope. For what the evidence builder is, see [Build an evidence pack](/evidence/build#set-up-the-evidence-builder).

## Make a seed for the signing key

Your agent signs every record with its signing key, an Ed25519 key made from a 32-byte seed. Make the seed once for each agent, with one of these commands. You keep it, and Sanning never receives it.

<CodeGroup>

```bash OpenSSL
openssl rand -hex 32
```

```bash Python
python -c "import secrets; print(secrets.token_hex(32))"
```

```bash Node.js
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

</CodeGroup>

Two agents never share a seed or an agent ID. The same command makes the seed of the hand-over key, which seals your evidence packs and stays with the evidence builder. For that key, see [Build an evidence pack](/evidence/build#set-up-the-evidence-builder). Sanning enrolls the signing key on your agent's first record, so you enroll nothing by hand.

To change the key later, rotate it: Sanning accepts a new key only when the old key signs the change. If a seed leaks, an owner or admin revokes the key in the console and re-keys the agent.

## Store both as environment variables

Put the seed and the API key of each agent in the secret store that your service already uses. The adapter guides read them from `SANNING_SIGNING_SEED` and `SANNING_API_KEY`. To follow along from a terminal, export both:

```bash
export SANNING_SIGNING_SEED=SEED
export SANNING_API_KEY=API_KEY
```

Replace the following:

- `SEED`: the 64 hex characters that you made.
- `API_KEY`: the Live API key that you copied.

Never commit either value to your code.

## Install the SDK

Install the SDK, the package that signs records and sends them to Sanning, with S3 support for your log store:

<CodeGroup>

```bash TypeScript
npm install @sanning/anchor @aws-sdk/client-s3
```

```bash Python
pip install "sanning-anchor[s3]"
```

</CodeGroup>

In TypeScript, `@aws-sdk/client-s3` is the AWS S3 library, which the SDK uses to reach your bucket and does not install for you. Each adapter guide shows how to install its adapter: a separate package in TypeScript, part of `sanning-anchor` in Python.

## Set up your log store

A log store is your own S3 bucket for the content of each record. Sanning gets only hashes, so the content stays with you, and you need it to build an evidence pack. In Live, the SDK does not record without a log store.

Use one bucket for all your agents. Each agent writes to its own folder in it, named after its agent ID, so that each agent's content stays apart.

1. Choose a bucket name, and put it and its Region in environment variables:

   ```bash
   export SANNING_LOG_BUCKET=BUCKET
   export AWS_REGION=REGION
   ```

   Replace the following:

   - `BUCKET`: the name you choose for your bucket.
   - `REGION`: the AWS Region for the bucket, such as `eu-west-1`. The SDK creates the bucket in this Region. It has no default Region: with no `AWS_REGION`, no `region` in code and no Region in your AWS config, the first record fails before any request, and the error names `AWS_REGION`.

2. If the agent runs on AWS with a role, skip this step. Otherwise, set the storage keys as environment variables:

   ```bash
   export AWS_ACCESS_KEY_ID=ACCESS_KEY_ID
   export AWS_SECRET_ACCESS_KEY=SECRET_ACCESS_KEY
   ```

   Replace the following:

   - `ACCESS_KEY_ID`: the access key ID of your storage keys.
   - `SECRET_ACCESS_KEY`: the secret access key of your storage keys.

   The keys must be able to create, write to and read from the bucket. For the list, see [The exact AWS permissions](#the-exact-aws-permissions). Both SDKs look for keys the way AWS tools do: environment variables, then the shared config file, then an instance or task role.

Without keys, the first record fails with a `RetentionError`, and nothing is sent to Sanning. The message ends with `Could not load credentials from any providers` in TypeScript and `NoCredentialsError: Unable to locate credentials` in Python. A direct `anchor` call throws the error. The LangChain adapter logs `step not anchored` for each step instead, and the agent keeps running with gaps in its trail.

On the agent's first record, the SDK creates the bucket with versioning and Object Lock in governance mode for 365 days. For that time, only a user who holds the AWS permission `s3:BypassGovernanceRetention` can delete or overwrite a stored version. If the bucket exists already, the SDK uses it and does not change it. It does not add Object Lock to a bucket that has none, so make a new bucket in that case.

<AccordionGroup>
  <Accordion title="The exact AWS permissions">
    Replace `BUCKET` with the name of your bucket.

    For the agent that records, on `arn:aws:s3:::BUCKET`: `s3:CreateBucket`, `s3:PutBucketVersioning`, `s3:PutBucketObjectLockConfiguration`, `s3:ListBucket`, `s3:GetBucketVersioning` and `s3:GetBucketObjectLockConfiguration`. On `arn:aws:s3:::BUCKET/*`: `s3:PutObject` and `s3:GetObject`. The first three create the bucket. The three reads let the SDK check that the bucket exists and is protected. Without them, the SDK warns that it cannot check. Before each write, the SDK reads the bucket to check that no other record uses the same event ID, so without `s3:GetObject` every record fails with an access error.

    After the agent's first record, you can remove `s3:CreateBucket`, `s3:PutBucketVersioning` and `s3:PutBucketObjectLockConfiguration` from its credential.

    No credential needs `s3:DeleteObject`.
  </Accordion>

  <Accordion title="Other S3-compatible stores">
    Sanning is built and tested for Amazon S3. Support for other storage providers is coming.

    The SDK might work with another service that has an S3-compatible API. Test it yourself before you rely on it. Set `SANNING_LOG_BUCKET` and `AWS_REGION` as in step 1, then set the service's address and keys:

    ```bash
    export AWS_ENDPOINT_URL_S3=ENDPOINT
    export AWS_ACCESS_KEY_ID=ACCESS_KEY_ID
    export AWS_SECRET_ACCESS_KEY=SECRET_ACCESS_KEY
    ```

    Replace the following:

    - `ENDPOINT`: the address of the service's S3 API, from its documentation.
    - `ACCESS_KEY_ID` and `SECRET_ACCESS_KEY`: the service's keys.

    If the service does not support Object Lock, the SDK warns and creates a plain bucket. The content is then not protected from deletion.

    Using another store? [Tell us which one](https://calendar.app.google/Znof4jp6fordTjhW6).
  </Accordion>
</AccordionGroup>

## Create the anchorer

The anchorer signs your records and sends them to Sanning. It needs your API key, your seed, an agent ID and your log store, with the agent's own folder in it. Every adapter uses this anchorer.

<CodeGroup>

```ts TypeScript
import {
  createAnchorer,
  LocalEd25519Signer,
  MemoryStore,
  ObjectLogStore,
} from "@sanning/anchor";
import { S3ObjectStore } from "@sanning/anchor/s3";

const logStore = new ObjectLogStore(
  new S3ObjectStore({
    bucket: process.env.SANNING_LOG_BUCKET!,
  }),
  { prefix: "claims-triage" },
);

const anchorer = createAnchorer({
  signer: LocalEd25519Signer.fromSeedHex(process.env.SANNING_SIGNING_SEED!),
  subject: { type: "agent", agent_id: "claims-triage" },
  apiKey: process.env.SANNING_API_KEY!,
  logStore,
  store: new MemoryStore(),
});
```

```python Python
import os

from sanning_anchor import (
    Anchorer,
    LocalEd25519Signer,
    MemoryStore,
    ObjectLogStore,
)
from sanning_anchor.s3 import S3ObjectStore

log_store = ObjectLogStore(
    S3ObjectStore(
        bucket=os.environ["SANNING_LOG_BUCKET"],
    ),
    prefix="claims-triage",
)

anchorer = Anchorer(
    signer=LocalEd25519Signer.from_seed_hex(os.environ["SANNING_SIGNING_SEED"]),
    subject={"type": "agent", "agent_id": "claims-triage"},
    api_key=os.environ["SANNING_API_KEY"],
    log_store=log_store,
    store=MemoryStore(),
)
```

</CodeGroup>

Both samples read the Region of the bucket from `AWS_REGION`. Replace `claims-triage`, in the `agent_id` and in the `prefix`, with the agent ID of your agent, and keep it stable: it is how the agent shows on the **Agents** page, and the name of its folder in the log store. Two agents must never share an agent ID.

`MemoryStore` keeps the last record of each chain in memory. Each adapter run has its own chain of records, so the SDK's warning about a durable chain store does not apply, and the `store` line turns that warning off.
