You have a pack and you want to check it yourself. You need Node and nothing else. You do
not need a Sanning account, an API key, or any cooperation from the party who gave you the
pack.

## The two steps

A pack is a zip. The kernel reads the bundle inside it, so extract first.

```bash
unzip pack.zip -d pack
cd pack
npx @sanning/proof verify bundle.json --logs logs/
```

A verified pack prints **Verified**, then a witness line, then its per-record results,
and exits **0**:

```
Verified
Witness: Not checked: no lookup was run
```

Leave out `--logs` when the pack has no `logs/` directory. A pack of hand-off
records has none, and `--logs` naming a directory that does not exist exits 4.

**From 0.17.0, a `--logs` folder is read by one rule.** The command reads each
regular file named `<event_id>.json` as that record's disclosed content. It never
follows a link, never enters a subfolder, and names every other entry in a `note:`
line without reading it. It exits 4 for a name that is not valid UTF-8, for more than
50,000 entries, and for more than 1 GiB of `<event_id>.json` files. Both
`@sanning/proof` and `sanning-proof` apply the same rule, so one folder no longer reads
differently in the two.

## Exit codes

This is the one table every verb of `@sanning/proof` and `sanning-proof`
uses, `verify`, `export` and `case` alike:

| Code | Name | Means |
|---|---|---|
| 0 | verified | The verdict is `verified` and no record is signed `environment: "dev"`. For `export`: the export was written |
| 1 | failed | The verdict is `failed`, for either reason kind. A Sandbox pack that fails also exits 1 |
| 2 | incomplete | The verdict is `incomplete`. A Sandbox pack that is incomplete also exits 2 |
| 3 | sandbox | The verdict is `verified` and a record is signed `environment: "dev"`: sandbox evidence, not production evidence |
| 4 | could not run | A bad flag, a missing file, or an input that is not a pack or a case at all |

The first line of the output is the title: **Verified**, **Failed** or **Incomplete**,
and the lines after it name the claims behind it. See
[What a verdict means](/verify/what-a-verdict-means).

A pack whose declaration says a record's content is withheld on purpose still
reads `verified`: a hand-off record commits to a message's hash and the pack
carries no file for it, and the declaration says so, so its content binding
is not a gap. A pack with **no** declaration (built
with no signing seed) and a record that discloses nothing reads `incomplete`
instead (exit 2), because nothing says the absence was on purpose. Either way the
signatures, the inclusion proofs and the declaration, where the pack has one,
are still checked, and the output says so on its own lines.

This command reads one pack. To read several parties' packs as one case, see
[Hand over and verify a case](/guides/handoff-case#read-the-case-at-the-command-line).

<Note>
  **From 0.14.0, `--files` matches a file beside the pack to the record that commits to
  it.** Each offered file is hashed and checked against `event.content_hash`, or a file
  part's `content_hash` inside a hand-off message. A file is never matched by name, and
  `case` takes the same flag. See [Command line](/reference/cli#verify).
</Note>

<Note>
  **From 0.17.0, `--files` accepts a folder.** The folder stands for the regular files
  inside it, found recursively with hidden files included, and each is matched by
  SHA-256 as a named file is. Links are never followed. A pipe is not read, and a file that cannot be read is
  attempted and then named as skipped (`unreadable`); the report names each in a
  `skipped` list with the reason. A folder
  nested more than 32 levels deep, holding more than 50,000 names, or holding a name
  that is not valid UTF-8 exits 4. Files found inside folders share 1 GiB per run, and
  one that would pass it is skipped as `too_large`. A file you name is read at any size.
  You can mix files and folders, and the verdict and exit code never move.
</Note>

<Note>
  **From 0.17.0, a reading fails closed on a tree size it cannot trust.** An anchor-trace
  event whose `inclusion.leaf_count` differs from the `leaf_count` its signed checkpoint
  carries reads `failed`, and so does a checkpoint record with no integer `leaf_count`.
  A stamp inclusion whose stated count is a boolean reads `failed` in both kernels.
  Integers on the anchor-trace, stamp, and agent-proof paths are read by value, so `3.0`
  is 3 and an honest bundle written with `3.0` verifies.
</Note>

<Note>
  **From 0.14.0, parsing is stricter.** A repeated key anywhere in the bundle file or a
  `--logs` map exits 4. `event_id`, `payload_hash`, `payload_ref`, `subject`, and every
  time field a verdict carries, are checked against their exact wire shapes rather than
  accepted as any string. Nothing on the public record is affected.
</Note>

## A Sandbox pack

A pack built in the Sandbox passes its checks and prints **Verified**, then a
Sandbox line. It exits **3**:

```
Verified
Sandbox: these records are sandbox records, not production evidence.
Witness: Not checked: no lookup was run
```

The exit code stays 3 with `--gateways`, because a Sandbox stamp is simulated and no
gateway can look it up. A failure is still 1, and an incomplete pack is still 2. See
[What a verdict means](/verify/what-a-verdict-means#what-a-sandbox-verdict-means).

## Two errors you might hit first

Both exit 4, before any check runs.

**You pointed it at the zip.** The kernel reads JSON, not an archive. `npx @sanning/proof`
prints the parser's message, and `sanning-proof` prints Python's:

```
pack.zip is not valid JSON: Unexpected token 'P', "PK\x03\x04\x14\x00\x00\x00\x00\x00"... is not valid JSON
pack.zip is not valid JSON: Expecting value: line 1 column 1 (char 0)
```

Extract the zip and point at `bundle.json` inside it.

**You pointed it at the directory.** The two commands again word the reason in their
own runtime's terms:

```
cannot read pack/: EISDIR: illegal operation on a directory, read
cannot read pack/: [Errno 21] Is a directory: 'pack'
```

Name `bundle.json`, not the folder that holds it. Only `--logs` and `--files` take a
folder.

## Check the tamper-evidence yourself

Do not take the verdict on trust. Break the pack and watch it fail.

```bash
# Change one byte of any disclosed log
printf 'x' | dd of=logs/SOME_EVENT_ID.json bs=1 seek=200 conv=notrunc

npx @sanning/proof verify bundle.json --logs logs/
```

It exits 1 and names the record you touched. Replace `SOME_EVENT_ID` with any filename
from `logs/`.

<Note>
  Confirm the file actually changed, with `sha256sum` before and after. An edit that
  writes the same byte back produces an identical file, which verifies clean and looks
  exactly like a passing tamper test.
</Note>

## Confirm the witness on the public record

The verdict above is offline. It names a witness without contacting it. To check that the
witness holds those bytes, pass a gateway:

```bash
npx @sanning/proof verify bundle.json --logs logs/ --gateways https://turbo-gateway.com
```

That turns a claim you read into one you checked. See
[What a verdict means](/verify/what-a-verdict-means) for why the two are different.

Any Arweave gateway works, and passing more than one is a comma-separated list.
Nothing binds you to the one we name: that independence is the point, and
checking through a gateway you chose is a stronger result than checking through
ours.

<Note>
  **Only an `arweave` witness with a 43-character transaction id is re-fetched.**
  That is the one witness kind and id shape the kernel knows how to look up. A
  witness of any other kind, or an `arweave` witness whose id is not exactly 43
  characters, is reported as not checked on the witness line rather than skipped silently. The
  lookup does not move the verdict or the exit code. Only a lookup that finds other
  bytes does: it disproves `witnessed`, and the run exits `1`.
</Note>

<Note>
  **From 0.16.0, a pack can carry `witness-cache.json` beside `bundle.json`.** It names
  a witnessed time the pack's own builder already looked up. This offline check prints
  it labelled not checked; pass `--gateways` to check it yourself.
</Note>

<Note>
  **A stamp reaches the chain before an index can serve it.** It is submitted,
  then bundled, then indexed, so a gateway can answer `404` for a few minutes
  on a stamp that exists. The witness line says the lookup was not settled, and
  the verdict and exit code do not move. It is a statement
  about reachability rather than about your evidence. The offline check does
  not wait on any of it. Retry the online one.
</Note>

## Python

`sanning-proof` on PyPI is the same kernel and ships **the same command**, so a
Python shop needs no Node to check a pack:

```bash
pip install sanning-proof
sanning-proof verify bundle.json --logs logs/
```

The verbs, the flags and the exit codes match `npx @sanning/proof` exactly.
Both kernels are graded against one corpus, and a disagreement between them on
the same input is release-blocking.

Use it as a library instead when you are checking a pack inside your own code:

```python
import json, pathlib
from sanning_proof.evidence import verify_evidence_bundle

bundle = json.load(open("bundle.json"))
content = {p.stem: p.read_bytes() for p in pathlib.Path("logs").glob("*.json")}

result = verify_evidence_bundle(bundle, content=content)
print(result.status)
```

`result.status` is the status of the signed bundle alone. It reads `verified` when the
signature, the inclusion proofs and the disclosed bytes hold, even for a pack the
command line reads `incomplete`, such as one whose closing record lists records the
pack does not hold. The pack verdict is the one `read_case` (`readCase` in
TypeScript) returns for the pack as a case of one: see
[What a verdict means](/verify/what-a-verdict-means#a-verdict-over-a-case).

Two kernels, one corpus. They agree record by record, and disagreeing is a bug we treat as
release-blocking.
