You have been handed an evidence pack and the kernel printed **Verified**. This page tells
you exactly what you may conclude from that, and what you may not.

The limits are specified in `evidence-bundle.md` section 5.3.4, which ships inside the
`sanning-proof` package and is the normative source. This page is the plain
reading. See [Wire formats](/reference/wire-formats) for how to open it.

## What a verified pack proves

For every event in the pack:

- **The agent signed it.** An Ed25519 signature over the envelope, checked against the
  public key embedded in the artifact.
- **The record matches its commitment**, where the agent disclosed the bytes. The
  disclosed record hashes to the `payload_hash` the signature covers.
- **It was included in the witnessed set.** An RFC 9162 inclusion proof from the event's
  leaf to the Merkle root committed inside the signed stamp.

All of it offline, against keys and bytes inside the pack. No call to Sanning, and no
account.

## Six claims, three verdicts

The kernel checks six claims. Each claim is `proven`, `disproven` or `not_proven`. A
claim with nothing to check, such as `agreed` in a pack with no hand-off, is not in
scope and the kernel does not print it.

| Claim | The kernel asks |
|---|---|
| `signed` | Did the key that the pack or record names sign it? |
| `unchanged` | Do the bytes agree with what was signed? |
| `witnessed` | Does a stamp cover each record, and does the stamp verify? |
| `complete` | Does the pack hold everything its own signed declaration and its stamp say it holds? |
| `agreed` | Do the two sides of each hand-off agree? |
| `follows_rules` | Does each record follow the vocabulary it names? |

A `not_proven` claim has one reason: `missing` (something is not in the pack),
`unreadable` (it is there and the kernel cannot read it) or `not_checked` (this
kernel cannot check it, for example a record written in a newer vocabulary version).

The kernel turns the six claims into one verdict by one rule, at every level: a
record, a hand-off, a pack, a case.

There are three verdicts and no others:

| Verdict | Shown as | Means |
|---|---|---|
| `verified` | **Verified** | Every claim in scope is proven |
| `failed` | **Failed** | At least one claim is disproven |
| `incomplete` | **Incomplete** | No claim is disproven, and at least one is not proven |

A `failed` verdict also carries a reason kind. It is `changed` when a disproven claim is
`signed`, `unchanged`, `witnessed`, `complete` or `agreed`. It is `nonconforming` when
the only disproven claim is `follows_rules`. When both hold, the reason kind is
`changed`. Sandbox is a label on the result and never a claim or a verdict. See
[What a Sandbox verdict means](#what-a-sandbox-verdict-means).

## What it does not claim

<Warning>
  Four boundaries. A verified verdict is a narrower statement than it first reads as, and
  relying on the wider reading is how evidence gets over-trusted.
</Warning>

**It is not completeness.** A pack proves the events it carries were committed to that
root. It says nothing about events the agent chose not to include. "Every step is
here" is not a claim this artifact can make. If completeness matters to you, ask the
agent what the pack covers and check that claim separately.

Three different things get called completeness, and only the first two are proved
here:

| Claim | Proved by |
|---|---|
| Nothing was removed from the middle of a run you were shown | The event chain: a deleted record leaves a hole and a dangling pointer |
| Nothing was dropped from what the stamp covered | The inclusion proofs, against the agent's own leaf count inside the stamp |
| You were shown every run there was | **Nothing.** No artifact can make this claim |

<Warning>
  **Two different leaf counts sit in a pack, and the obvious one is the wrong one for
  this.** `inclusion.leaf_count`, and the stamp's top-level `leaf_count`, count the whole
  organization's tree for that interval, so they include every other agent's records.
  Reading a pack as short because it shows fewer events than that number is a false
  alarm in any organization running more than one agent.

  The number that describes one agent's slice is `subtrees[ref].leaf_count` inside
  `stamp_bytes`, which is exact for that agent in that interval. Its `ref` is blinded
  with a secret only the producing organization holds, so **the agent can check their
  own slice and a third party cannot map a subtree to an agent** unless the agent
  discloses the ref. That blinding is deliberate: it is what keeps one customer's list of
  agents out of another reader's hands.
</Warning>

**It is not proof the chain was consulted.** A `verified` verdict is offline and
internally consistent, and it *names* a witness. Confirming that the witness actually
holds those bytes is a separate, online act. Run the kernel with a gateway to do it, or
fetch the transaction yourself.

**It is not identity.** The envelope carries a public key, and a key is not a person.
Binding a key to an organization happens out of band. Agent identity informs a reader;
it never gates verification.

**It is not a statement about a per-agent slice.** A stamp covers an interval across a
whole organization. The pack carries only its own events, so it cannot tell you what else
that organization anchored in the same interval.

<Note>
  **From 0.14.0, a verified drop carries one reliance sentence.** Every pack and every
  case reading states, in one sentence, what a `verified` result there means you can
  rely on, and names a hand-off clause only when the drop actually holds a hand-off. It
  replaces wording written for a hand-off reading that read oddly on a pack holding only
  one agent's own steps.
</Note>

## What a Sandbox verdict means

A pack built in the Sandbox passes every check and still ends in a different exit code
from a Live pack. The kernel prints **Verified**, adds the line "Sandbox: these records
are sandbox records, not production evidence.", and exits 3. The browser page shows
**Sandbox** in place of the verified verdict.

The signatures, the inclusion proofs and the disclosed bytes all checked out, so the
records are intact and attributed. What is missing is the witness: a Sandbox stamp is
simulated, so it supplies no independent time and no public record holds it. Read a
Sandbox pack as a rehearsal. Do not rely on it as evidence.

A Sandbox pack that fails still exits 1, and one that is incomplete still exits 2. The
kernel reads the marker from the signed records in the pack, not from a field anyone
can edit without a key, and no flag turns exit code 3 into 0. See
[Sandbox and live](/concepts/sandbox-and-live).

## What a failure means

If the kernel prints **Failed**, it names each claim that was disproven, how many
records it concerns and why. The next line says what to do. Read the title first:

- **Failed: do not rely on this evidence.** The reason kind is `changed`. Something
  does not match what was signed, such as a bad signature, bytes that differ from
  their commitment, or two sides of a hand-off that signed different messages.
- **Failed: a record does not follow the rules.** The reason kind is `nonconforming`.
  A record is signed and intact and breaks the vocabulary it names. Examples are a type
  outside the closed set of event types, a field the type does not name, and a
  `context.salt` that is not 32 lowercase hex characters. Nothing was proven altered:
  the producer wrote something the specification does not allow.

A bundle can carry a `verdict` member from whoever built it. The kernel never reads it.
It computes the verdict from the claims on your machine, so you are not reading the
agent's claim about their own evidence. You are reading your own machine's answer.

## What each verdict does not mean

- **Verified** does not mean the agent decided correctly, that everything that happened
  was recorded, that the evidence complies with a rule or a law, or that the key belongs
  to the organization named in the pack. It does not mean the public record was
  checked, unless the witness line says so.
- **Failed** does not mean anyone acted in bad faith. A failed `unchanged` means the
  bytes changed after signing, not who changed them. A failed `follows_rules` means
  nothing was proven altered.
- **Incomplete** does not mean anything is wrong. Nothing was proven wrong, and
  something could not be checked. It is not "verified with a warning": do not rely on
  the parts that are not proven.

**Absent evidence is reported as absent, never as failure.** If an agent withheld the
bytes for a record, `unchanged` is `not_proven` for that record and the pack reads
`incomplete`, unless the pack's own signed declaration says the agent withheld them on
purpose. That is an agent exercising minimum disclosure, not a defect, and treating it
as tampering would be wrong. Input the kernel cannot read, such as a `bundle.json` that
does not parse, is `not_proven` with the reason `unreadable`. It reads `incomplete`,
never `failed`.

Findings and notes never move a verdict. The kernel prints a finding as a line that
starts "Note:".

## What the kernel prints

The kernel renders the words once, and the text report and `--json` both carry those
words. The report has this shape:

```
<Title>
<one line for each claim that is disproven or not proven>
Next: <one next action>
Note: <one line for each note>
Sandbox: these records are sandbox records, not production evidence.
Witness: <the witness line>
```

The kernel prints only the lines that apply. The `--json` output carries the same words
in `person`. See [Command line](/reference/cli#verify) for the members.

## A verdict over a case

A case reading is one reader's reading over the packs it was handed: several
packs that together hold both sides of one or more hand-offs, often from two
organizations. A reader drops every pack together and gets one **case
verdict**, with every exception named. It needs `@sanning/proof` or
`sanning-proof` 0.13.0 or later. A formed pair verifies only when each record
names the other's signer, and a pair that does not fails the check
`counterparty_named`.

A case reads its worst pack: `failed`, then `incomplete`, then `verified`. The kernel
lists every problem in every pack. Each kind of exception maps to one claim and one
state, as the following table shows:

| Group | Example | Claim and state | Verdict |
|---|---|---|---|
| Something is proven wrong | The two sides of a hand-off commit to different messages | `agreed` disproven | `failed` |
| A record breaks its vocabulary | A record's type is outside the closed set | `follows_rules` disproven | `failed` |
| Something is not in a readable form | A pack's `bundle.json` is not valid JSON | The claim it blocks is `not_proven`, reason `unreadable` | `incomplete` |
| The reader could not tell | No pack signed by the key one side of a hand-off names is in what you dropped | `agreed` `not_proven`, reason `missing` | `incomplete` |
| Something was not there to read | A pack does not say what it holds | `complete` `not_proven`, reason `not_checked` | `incomplete` |

Two more leave `agreed` `not_proven`: more than one record on the other side could be a
hand-off's counterpart (fan-in, fan-out, or several messages one way), and a pack
declares a record under the wrong **role**: a record marked `handoff` that no pair
claims, or a record marked `step` that is actually a hand-off side. A candidate that
another record already accounts for is set aside before the reader grades, so an honest
exchange of several messages in one direction reads `verified`. A **step record**, such
as a closing record, is signed as one under `sanning.declaration/v2` and sits outside the
hand-off scope test entirely, so a full pack, hand-offs and step records together, reads
cleanly. [What a hand-off record does not prove](/concepts/limits) says what each
exception looks like and why the reader cannot resolve it on its own.

One kind carries a pack's own verdict instead: a pack whose signature holds and
which does not verify on its own passes its verdict to the case, so a case never
reads better than its weakest pack. A pack whose declaration says a record's
content is withheld on purpose is not one of these: it still reads `verified`,
and the reading's **notes** (never an exception) say how many records are
withheld.

**A missing side is an exception, never a failure.** No pack signed by the
counterparty's key was in what you dropped; that is not proof the counterparty
recorded nothing, and it is not tampering. The kernel prints each exception in
its own words, under a **scope sentence** that names the packs, the signing
keys, the hand-off records and the exceptions in the reading, and a **witness
line** that says whether any witness was looked up on the public record,
independently of the headline.

To read a case from your own code, pass the packs to `readCase` (`read_case`
in Python). The `case` command does the same from a terminal, as
[Hand over and verify a case](/guides/handoff-case#read-the-case-at-the-command-line)
shows.

<CodeGroup>

```js JavaScript
import { readFile, readdir } from "node:fs/promises";
import {
  readCase,
  renderCaseSummary,
  renderCaseNote,
  renderException,
} from "@sanning/proof";

// One pack: its bundle.json, and every log file beside it, keyed by event id.
async function pack(dir) {
  const bundle = JSON.parse(await readFile(`${dir}/bundle.json`, "utf8"));
  const content = {};
  // A pack of hand-off records only has no logs/ directory.
  const names = await readdir(`${dir}/logs`).catch(() => []);
  for (const name of names) {
    content[name.replace(/\.json$/, "")] = await readFile(`${dir}/logs/${name}`);
  }
  return { ref: dir, bundle, content };
}

const reading = await readCase(
  await Promise.all(process.argv.slice(2).map(pack)),
);
console.log(reading.verdict);
console.log(renderCaseSummary(reading));
for (const exception of reading.exceptions) {
  console.log(renderException(exception));
}
for (const note of reading.notes) {
  console.log(renderCaseNote(note));
}
```

```python Python
import json
import sys
from pathlib import Path

from sanning_proof import (
    CasePack,
    read_case,
    render_case_note,
    render_case_summary,
    render_exception,
)


def pack(directory: str) -> CasePack:
    root = Path(directory)
    bundle = json.loads((root / "bundle.json").read_text(encoding="utf-8"))
    content = {log.stem: log.read_bytes() for log in (root / "logs").glob("*.json")}
    return CasePack(ref=directory, bundle=bundle, content=content)


reading = read_case([pack(d) for d in sys.argv[1:]])
print(reading.verdict)
print(render_case_summary(reading))
for exception in reading.exceptions:
    print(render_exception(exception))
for note in reading.notes:
    print(render_case_note(note))
```

</CodeGroup>

**From 0.17.0, the reading names every pack, record, exception and note by
position, not by `ref`.** Two packs can carry one `ref`, and one pack can carry an
`event_id` twice, so a `ref` is a label for a person and never a join. The
following table lists the fields a consumer joins on. Only the TypeScript `readCase`
result is camelCase (`packIndex`); `case --json` from either command (`npx
@sanning/proof` or the Python `sanning-proof`) and the Python `read_case` use
`pack_index`.

| Part of the reading | Names its pack by | Names its record by |
|---|---|---|
| `packs` | `index`, the pack's position in the order you passed the packs, 0 first | Not applicable |
| `exceptions` | `pack_index`, present wherever the exception names a pack (optional in both kernels) | `record_index`, the record's position in its pack, where the exception is about one record |
| `notes` | `pack_index` | Not applicable |
| `records` | `pack_index` | `record_index` |

`records` lists every record of every pack, not only the ones that were read.
Each carries a `status`:

- `read_clean`: the record went into the reading and no exception or declaration
  finding names it. The status says nothing about its pack, so read the pack's
  grade beside it.
- `read_flagged`: the record went into the reading, and an exception or a
  declaration finding names it.
- `not_read`: the record never went into the reading. Its `reason` is the kind of
  the exception that says why.

A consumer that joined by `ref`, or read `records` as "the records that were
read", must change. No verdict, exception kind, contribution or exit code moves.

Run it with one directory per pack, each holding `bundle.json` and, when the
pack has one, `logs/`. Over an honest case with every record's content
disclosed, the first line is the verdict word and the second is the scope
sentence:

```
verified
2 pack(s), 2 signing key(s), 4 hand-off record(s), 0 exception(s), read offline.
```

Over a case whose two sides disagree, the output includes the verdict word and one
line for each side of the hand-off that failed:

```
failed
assessor-pack/a634bed2-0495-461b-ac51-b092f09fbb72 failed on message_hash
reviewer-pack/93d88dca-4dbb-4ec3-997f-5299135efdc6 failed on message_hash
```

A case verdict carries the same limits as a pack verdict, and more:
[What a hand-off record does not prove](/concepts/limits) states them.
