You have been handed an evidence pack and the kernel printed `VERIFIED`. This page tells
you exactly what you may conclude from that, and what you may not.

The limits are specified in `evidence-bundle.md` §5.3.4, which ships inside the
`sanning-proof` package and is the normative source. This page is the plain
reading. See [Wire formats](/reference/wire-formats) for how to open it.

## What a verified pack proves

For every event in the pack:

- **The agent signed it.** An Ed25519 signature over the envelope, checked against the
  public key embedded in the artifact.
- **The record matches its commitment**, where the agent disclosed the bytes. The
  disclosed record hashes to the `payload_hash` the signature covers.
- **It was included in the witnessed set.** An RFC 9162 inclusion proof from the event's
  leaf to the Merkle root committed inside the signed stamp.

All of it offline, against keys and bytes inside the pack. No call to Sanning, and no
account.

## What it does not claim

<Warning>
  Four boundaries. A verified verdict is a narrower statement than it first reads as, and
  relying on the wider reading is how evidence gets over-trusted.
</Warning>

**It is not completeness.** A pack proves the events it carries were committed to that
root. It says nothing about events the agent chose not to include. "Every step is
here" is not a claim this artifact can make. If completeness matters to you, ask the
agent what the pack covers and check that claim separately.

Three different things get called completeness, and only the first two are proved
here:

| Claim | Proved by |
|---|---|
| Nothing was removed from the middle of a run you were shown | The event chain: a deleted record leaves a hole and a dangling pointer |
| Nothing was dropped from what the stamp covered | The inclusion proofs, against the agent's own leaf count inside the stamp |
| You were shown every run there was | **Nothing.** No artifact can make this claim |

<Warning>
  **Two different leaf counts sit in a pack, and the obvious one is the wrong one for
  this.** `inclusion.leaf_count`, and the stamp's top-level `leaf_count`, count the whole
  organization's tree for that interval, so they include every other agent's records.
  Reading a pack as short because it shows fewer events than that number is a false
  alarm in any organization running more than one agent.

  The number that describes one agent's slice is `subtrees[ref].leaf_count` inside
  `stamp_bytes`, which is exact for that agent in that interval. Its `ref` is blinded
  with a secret only the producing organization holds, so **the agent can check their
  own slice and a third party cannot map a subtree to an agent** unless the agent
  discloses the ref. That blinding is deliberate: it is what keeps one customer's agent
  roster out of another reader's hands.
</Warning>

**It is not proof the chain was consulted.** A `verified` verdict is offline and
internally consistent, and it *names* a witness. Confirming that the witness actually
holds those bytes is a separate, online act. Run the kernel with a gateway to do it, or
fetch the transaction yourself.

**It is not identity.** The envelope carries a public key, and a key is not a person.
Binding a key to an organization happens out of band. Agent identity informs a reader;
it never gates verification.

**It is not a statement about a per-agent slice.** A stamp covers an interval across a
whole organization. The pack carries only its own events, so it cannot tell you what else
that organization anchored in the same interval.

## What a failure means

If the kernel prints `FAILED`, it names the record that broke and why. The pack itself
carries an asserted verdict from whoever produced it, and **the kernel throws that away
and recomputes**. Where the two disagree, the recomputed answer wins, and the output
says the asserted verdict and the recomputed one by name, noting that the recomputed
one is the one that counts.

That is the property worth understanding. You are not reading the agent's claim about
their own evidence. You are reading your own machine's answer.

## What "undetermined" means

A pack can verify while leaving some things unknown, and the kernel distinguishes that
from failure on purpose.

| Verdict | Means |
|---|---|
| `verified` | Every check the pack supports passed |
| `failed` | A check ran and did not pass |
| `partial` | The pack is sound, and something could not be checked |
| `undetermined` | A check could not run at all |

**Absent evidence is reported as absent, never as failure.** If an agent withheld the
bytes for a record, its content binding is undetermined. That is an agent exercising
minimum disclosure, not a defect, and treating it as tampering would be wrong.

## A verdict over a case

A case is several packs that together hold both sides of one or more hand-offs,
often from two organizations. A reader drops them together and gets one
verdict, with every exception named. It needs `@sanning/proof` 0.11.0 or
`sanning-proof` 0.11.0.

The verdict is reached by one rule. Every hand-off whose two sides were found
and checked contributes a verdict, and so does every exception. If they all say
the same word, that word is the case verdict. If they differ, the case is
`mixed`. A case reads `verified` only when there is no exception at all.

Each kind of exception contributes one verdict word, as the following table
shows:

| Group | Example | Word it contributes |
|---|---|---|
| Something is proven wrong | The two sides of a hand-off commit to different messages | `failed` |
| Something is not in a readable form | A hand-off record is missing a field its type requires | `malformed` |
| The reader could not tell | One side of a hand-off is not in any pack you dropped | `incomplete` |
| Something was not there to read | A pack does not say what it holds | `partial` |

One kind carries a pack's own verdict instead: a pack whose signature holds and
which does not verify on its own passes its verdict to the case, so a case never
reads better than its weakest pack.

**A missing side is an exception, never a failure.** The other party may not
have handed its pack over, and absence is not tampering. The verify page prints
each exception in the kernel's own words, with a plain explanation beside it.

To read a case without the page, pass the packs to `readCase` (`read_case` in
Python). There is no command-line verb for a case in `@sanning/proof` 0.11.0.

<CodeGroup>

```js JavaScript
import { readFile, readdir } from "node:fs/promises";
import { readCase, renderException } from "@sanning/proof";

// One pack: its bundle.json, and every log file beside it, keyed by event id.
async function pack(dir) {
  const bundle = JSON.parse(await readFile(`${dir}/bundle.json`, "utf8"));
  const content = {};
  for (const name of await readdir(`${dir}/logs`)) {
    content[name.replace(/\.json$/, "")] = await readFile(`${dir}/logs/${name}`);
  }
  return { ref: dir, bundle, content };
}

const reading = await readCase(
  await Promise.all(process.argv.slice(2).map(pack)),
);
console.log(reading.verdict);
for (const exception of reading.exceptions) {
  console.log(renderException(exception));
}
```

```python Python
import json
import sys
from pathlib import Path

from sanning_proof import CasePack, read_case, render_exception


def pack(directory: str) -> CasePack:
    root = Path(directory)
    bundle = json.loads((root / "bundle.json").read_text(encoding="utf-8"))
    content = {log.stem: log.read_bytes() for log in (root / "logs").glob("*.json")}
    return CasePack(ref=directory, bundle=bundle, content=content)


reading = read_case([pack(d) for d in sys.argv[1:]])
print(reading.verdict)
for exception in reading.exceptions:
    print(render_exception(exception))
```

</CodeGroup>

Run it with one directory per pack, each holding `bundle.json` and `logs/`.
Over a case whose two sides disagree, both languages print the same lines:

```
failed
org-a-pack/handoff-sent-a1 FAILED on message_hash
org-b-pack/handoff-received-b1 FAILED on message_hash
```

A case verdict carries the same limits as a pack verdict, and more:
[What a hand-off record does not prove](/concepts/limits) states them.
