One API key belongs to your organization and covers all of your agents. It
authorizes the call. It never decides identity: that comes from each agent's
own signing key, which Sanning never receives.

This page is about the key.

## The prefix decides the mode

Each API key belongs to one mode, and its prefix says which. The mode follows the
key, so the same code, the same host and the same SDK call serve both. The following
table lists the prefixes.

| Mode | API key prefix | Created in |
|---|---|---|
| Sandbox | `sanning_test_` | The Sandbox, under **Settings, API keys** |
| Live | `sanning_prod_` | Live, under **Settings, API keys** |

A Live plane refuses a Sandbox API key with `SANDBOX_KEY_ON_LIVE`, and a Sandbox refuses
a Live API key with `LIVE_KEY_ON_SANDBOX`. A Sandbox holds at most 10 active API keys.
See [Sandbox and Live](/reference/api-keys#sandbox-and-live).

## Create a key

Access to `console.sanning.io` starts with a conversation with the Sanning
team, not a sign-up form. Once your organization is set up, open
**Settings, API keys** and select **Create key**. Only an owner or admin can
create one. Name the key, and leave **Verify** unchecked unless this key will
also ask Sanning for a verdict. Store it as `SANNING_API_KEY` in whatever your
service already uses for secrets. The key is a credential for your
organization, not the key that signs your evidence.

## What a key can do

A key can **anchor**, or **anchor and verify**. Those are the two choices, and
the console's **Create key** dialog is exactly that: a name, and whether the
key may verify.

The console shows the two words. The scope names behind them travel on the API
and appear inside a refusal, so they are worth recognizing:

| Choice | Scopes on the key |
|---|---|
| Anchor | `agent:enroll`, `anchor:write`, `anchor:read` |
| Anchor and verify | those three, plus `verify:submit` and `verify:read` |

**Those are the only two sets a key you create can carry.** Scopes are not
selected one at a time, and `POST /api/v1/user/keys` accepts nothing else: it
answers "A key can anchor, or anchor and verify. Send scopes with exactly the
three anchor scopes, or those three and the two verify scopes." The same
route takes only a name and the scope set. Sanning sets every other property
of the key.

The three anchor scopes travel together because each one is useless without
the others. A key that can write but cannot enroll anchors nothing, because
the plane refuses an envelope signed by a key it has no agent for. A key that
can write but cannot read anchors for months and then fails on the day someone
asks for a pack, because building one reads your own records back.

The **Verify** choice always appears in the dialog. Where your organization
does not have verify access, it appears disabled, with a sentence naming the
address to ask.

## Enrollment happens on the first anchor

You write no enrollment step. On the first `anchor` call the SDK proves
possession of the signing key to the control plane, and the agent appears on
the console's **Agents** page attributed to that key. One organization key
covers every agent: no per-agent credential, no enrollment script. See
[How an agent enrolls](/reference/api-keys#how-an-agent-enrolls) for the full lifecycle, including
revoking and re-keying an identity from the console.

Enrollment is the plane's door policy, and it is not the trust path. Every
signed record verifies offline against the open kernel whether or not the
key is enrolled.

Two properties are load-bearing:

- **The challenge is checked before it is signed.** Enrollment is the one
  moment your identity key signs bytes the server chose, and that key also
  seals your evidence. The SDK refuses anything that is not a nonce rather
  than trusting Sanning not to send an envelope pre-image. Sanning is never in
  the trust path, including here.
- **Re-enrolling the same key is a no-op.** So it can run
  on every boot.

## One signing key per agent

An agent's identity is its key, so a different key under a name your
organization has already enrolled is a rotation, and a rotation must be
authorized by the key being retired rather than by the API key. Generating a
key at process start therefore works on the first boot and fails on the second
with `RotationUnauthorizedError`.

Load the same 32-byte seed on every boot. When you do mean to rotate, pass the
retiring key so it can counter-sign the challenge:

<CodeGroup>

```ts TypeScript
const anchorer = createAnchorer({
  signer: LocalEd25519Signer.fromSeedHex(newSeedHex),
  subject: { type: "agent", agent_id: "claims-triage" },
  apiKey: process.env.SANNING_API_KEY,
  previousSigner: LocalEd25519Signer.fromSeedHex(retiringSeedHex),
});
```

```python Python
anchorer = Anchorer(
    signer=LocalEd25519Signer.from_seed_hex(new_seed_hex),
    subject={"type": "agent", "agent_id": "claims-triage"},
    api_key=os.environ["SANNING_API_KEY"],
    previous_signer=LocalEd25519Signer.from_seed_hex(retiring_seed_hex),
)
```

</CodeGroup>

A rotation is never inferred from a refusal. That is what stops a leaked
organization key taking over an identity that is already producing evidence.
If the retiring key is genuinely lost, an owner or admin revokes the agent's key, then
pins a new key for the agent from **Settings, Signing keys** in the console, and the
agent completes the re-key on its next boot. See
[Re-key a revoked name](/reference/api-keys#re-key-a-revoked-name).

## Enroll at deploy time instead

Where you would rather enroll out of band, turn the automatic call off and
drive it yourself. Agents that cold-start together share one rate limit,
because enrollment is limited per API key, so this is the answer to
`EnrollmentThrottledError` as well.

<CodeGroup>

```ts TypeScript
import { DEFAULT_BASE_URL, enroll } from "@sanning/anchor";

const apiKey = process.env.SANNING_API_KEY;
if (!apiKey) throw new Error("set SANNING_API_KEY");

await enroll({
  baseUrl: DEFAULT_BASE_URL,
  apiKey,
  agentId: "claims-triage",
  signer,
});
```

```python Python
from sanning_anchor import enroll

enroll(
    api_key=os.environ["SANNING_API_KEY"],
    agent_id="claims-triage",
    signer=signer,
)
```

</CodeGroup>

Then build the anchorer with `autoEnroll: false` in TypeScript, or
`auto_enroll=False` in Python.

## Two names travel, and they are not the same name

`subject.agent_id` is sealed inside every signed record. It is history, it
never changes, and it cannot contain spaces. A display name lives on the
console's **Agents** page and accepts any text. The console cannot rename an agent: pass
a new display name, and the next enrollment updates it.

They default to agreeing. Pass `displayName` to `createAnchorer` in
TypeScript, or `display_name` on the anchorer in Python, when you want a
human-readable label. Renaming an agent then never reaches back and rewrites
what a past record was signed saying.

## Scopes

An API key authenticates your organization. It is not the key that signs your evidence.

### The two sets

A key can **anchor**, or **anchor and verify**. The console shows those two
words; the scope names travel on the API and appear inside a refusal. They are
listed here to be recognized, not to be picked from.

| Choice | Scopes on the key |
|---|---|
| Anchor | `agent:enroll`, `anchor:write`, `anchor:read` |
| Anchor and verify | those three, plus `verify:submit` and `verify:read` |

**A key you create carries one of those two sets and nothing else.** Scopes are
not selected individually. `POST /api/v1/user/keys` refuses any other
combination, with its own message: "A key can anchor, or anchor and verify.
Send scopes with exactly the three anchor scopes, or those three and the two
verify scopes."

What each scope allows:

| Scope | Allows |
|---|---|
| `agent:enroll` | Enroll a signing key against an agent name |
| `anchor:write` | Anchor records |
| `anchor:read` | Read your own records back, which is how a pack is built and how `bundle` reports one |
| `verify:submit` | Ask Sanning for a verdict |
| `verify:read` | Read a verdict back |

### Why the three anchor scopes travel together

Each one is useless without the others, which is why they are one choice rather
than three.

- **`agent:enroll` runs first.** Both SDKs enroll the signing key before the
  first anchor, in the runtime, which is where the signing key is. A key that
  could write but not enroll would anchor nothing, because the plane refuses an
  envelope signed by a key it has no agent for.
- **`anchor:read` runs last.** Building a hand-over pack reads your own records
  back, and `bundle` reports each pack it writes with the same key. Anchoring
  never touches the read routes, so a key that could write but not read would
  work for weeks and fail the first time you hand anything over.

The verify pair is separate because it is a different act: asking Sanning for a
verdict, rather than producing evidence. An agent runtime never needs it. The
console's Create key dialog always shows the choice, disabled and with a
sentence naming the address to ask, where an organization does not have
verify access.

### What the signing key does, and what it never leaves

The API key and the signing key are different things and the split is the security model.

| | Held by | Reaches Sanning |
|---|---|---|
| API key | Your organization | Yes, as a bearer credential |
| Signing key | Your agent | Never |

Sanning cannot produce a record that verifies as yours, because it has never held the key
that signs one.

## How an agent enrolls

An agent's identity is its signing key, and nothing in the console creates
one. This page is the whole lifecycle: how a key enrolls itself, what makes a
key unique, and what an owner or admin does when a name needs a new one.

### Enrollment happens on the first anchor, not before

You write no enrollment step. The first time your agent calls `anchor`, the
SDK proves possession of its signing key to the control plane, and the agent
appears on the console's **Agents** page under that key. Enrolling is part of
what every key can do, so one organization API key covers every agent in your
organization.

Re-enrolling the same key on a later boot is a no-op, so it can run every time your
service starts.

### Sandbox and live identities

The Sandbox and Live are separate. An agent that enrolls in the Sandbox does not exist in
Live, and a signing key enrolled in one is not enrolled in the other. Going live means a
fresh enrollment: a new signing seed, a Live API key, and a first anchor against Live. See
[Move from the Sandbox to Live](/reference/api-keys#move-from-the-sandbox-to-live).

### One key, one agent name, forever

A signing public key is unique across all of Sanning, not only your
organization, and stays that way in any state, forever. Two rules follow from
that, and both SDK enrollment and the console's re-key enforce them:

- **A key already enrolled under another name is refused.** Registering it
  again under a different name would let one key sign for two identities.
  This is `SIGNING_KEY_ALREADY_ENROLLED` (409): for another name in your own
  organization, when the key is active or retired there; for a name in a
  different organization, whatever state the key is in there, including
  revoked. A key revoked under a name in your own organization gets the more
  specific refusal below instead. The error names no other organization.
- **A revoked key is refused everywhere, permanently.** Revocation repudiates
  the key itself, not only the name that held it, so no name, in any
  organization, may register it again. Inside your own organization the
  refusal is `SIGNING_KEY_PREVIOUSLY_REVOKED` (409); a key revoked in another
  organization is refused as `SIGNING_KEY_ALREADY_ENROLLED` (409), because a
  refusal that reaches across organizations says nothing about the state a key
  is in somewhere you cannot see. A key stays reserved even if the
  organization that enrolled it is later deleted.

Replicas of one agent share its name and key. Use a distinct key for every
agent you run, anywhere: a key one deployment already holds cannot enroll
under a second name or a second organization, and cannot come back after it
is revoked.

### Nothing in the console enrolls a key

**Settings, Signing keys** lists every key enrolled to sign an agent's
envelopes, but it has no **Create** action. A key's row exists because an
agent anchored with it, not because someone added it.

### Revoke an active key

An owner or admin opens **Settings, Signing keys**, finds the active key, and
selects **Revoke**. Revocation is scoped to your organization: it stops that
key from anchoring anything further for your organization, and it cannot be
undone by re-enrolling the same key, including by whoever holds it. Records
the key signed before revocation are untouched and still verify.

### Re-key a revoked name

A revoked name does not disappear and cannot enroll through the SDK again, so
recovering it takes both a console step and a runtime one.

1. Generate a new key pair where the agent runs, using the same tool you used
   the first time (`openssl rand -hex 32` produces a seed; derive the public
   half from it).
2. In **Settings, Signing keys**, an owner or admin selects **Re-key** on the
   revoked name and pastes the public key, as 64 hex characters. This step only
   reserves the key: it does not yet let the name anchor. A pin that is not
   claimed lapses after 7 days.
3. Restart the agent with the new seed. On its first anchor, the SDK's
   enrollment proves possession of the pinned key to the control plane, which
   completes the re-key and lets the name anchor again.

The public half is all the console ever needs. Sanning never sees the seed
that produced it, before or after a re-key. A pin that is never claimed can be
cancelled from the same **Settings, Signing keys** screen. Re-key refuses a
name that is not revoked (`SIGNING_KEY_NOT_REVOKED`, 409): a live key rotates
through the SDK instead, with the outgoing key's counter-signature. See
[Errors](/reference/errors) for both codes.

## Sandbox and Live

Sanning runs in two modes. The Sandbox is a rehearsal: records are signed for real, but
stamps are simulated and never reach the public record. Live publishes stamps to the
public record and produces evidence. You choose the mode with the API key you use, and
you change nothing else.

This section compares the two. To move an agent from one to the other, see
[Move from the Sandbox to Live](#move-from-the-sandbox-to-live).

### One host, and the API key decides

Both modes answer at the same two hosts. Use `https://api.sanning.io` for SDKs and
scripts, and `https://console.sanning.io` for people. Both hosts serve the Sandbox and
Live, and the SDKs work against either.

The prefix of the API key routes each request to the Sandbox or to Live. A request that
reaches the wrong plane is refused by name: a Live plane refuses a Sandbox API key with
`SANDBOX_KEY_ON_LIVE`, and a Sandbox refuses a Live API key with `LIVE_KEY_ON_SANDBOX`.
Neither refusal reads or writes your data. See [Errors](/reference/errors#sandbox-errors).

### Compare the modes

The following table lists what differs. A row that is not here is the same in both
modes: the SDK calls, the record format, the log store, the pack and the verify commands.

| | Sandbox | Live |
|---|---|---|
| Host | `api.sanning.io` and `console.sanning.io` | The same two hosts |
| API key prefix | `sanning_test_` | `sanning_prod_` |
| Signed `environment` | `"dev"`, set for you by the API key | `"production"`, set for you by the API key |
| Records | Signed for real | Signed for real |
| Stamp | Simulated. Never reaches the public record | Published to the public record |
| How long a stamp takes | About a minute | Set by the witness interval. See [Wait for the stamp](/guides/evidence#wait-for-the-stamp) |
| Retention | Deleted after 30 days | Permanent |
| Ceilings | Fixed. See [Limits](/reference/errors#limits) | Set by your plan |
| Reset | Deletes your Sandbox data on request | None. Records cannot be withdrawn |
| Email | None sent | Unchanged |
| Billing | Never billed | Billed by plan |
| Verify page | Shows the result, with a Sandbox line | Shows the result |
| Verify CLI | Prints a Sandbox line and exits 3 | Exits 0 on a verified pack |

The wire values in this table are the only place this documentation names them. Everywhere
else it says Sandbox and Live.

### What stays the same

The records are real in both modes. An agent signs each record with its own signing key,
the hash is computed on your machine, and the pack verifies with the same open kernel.
Only the stamp is simulated in the Sandbox.

That makes a Sandbox pack a faithful rehearsal of a Live one.

### How you enter the Sandbox

A Sandbox organization exists only by entry from a Live organization. Sign in on Live,
open the account menu and select **Switch to sandbox**. Verify your email address first,
or the entry is refused with `EMAIL_NOT_VERIFIED`.

In the Sandbox, a strip runs across the top of the console with **Switch to live**.
**Settings** has **API keys**, **Signing keys** and **Sandbox**. The **Sandbox** page holds
**Reset the sandbox**.

A Sandbox follows its Live organization: when Live archives or deletes the organization,
the Sandbox does too.

### Retention and reset

Sandbox data older than 30 days is deleted daily. To clear it sooner, an owner or admin
selects **Reset the sandbox** under **Settings, Sandbox** and types the organization's
name to confirm. A Reset:

- Deletes every record, stored envelope, stamp and pack report.
- Keeps your API keys and signing keys, so your integration keeps working.
- Marks every agent decommissioned, which frees the agent ceiling.

A Reset runs once every 5 minutes per organization. Deleted records cannot be restored,
and a Reset never touches Live.

### A pack carries one mode

The `bundle` command refuses to assemble a window that mixes Sandbox and Live evidence
for one agent. A mixed pack would leave the reader to notice which is which, and the
reader's whole task is deciding what the evidence supports. Give the Sandbox version of
an agent its own `agent_id`, such as `claims-triage-dev`: Sandbox and Live identities are
separate, as [How an agent enrolls](/reference/api-keys#sandbox-and-live-identities)
explains.

### Move from the Sandbox to Live

Your code does not change: the SDK reads the API key. Three things do:

1. Make a Live API key, in Live under **Settings, API keys**.
2. Make a new signing seed for Live. A key that is enrolled in the Sandbox is not enrolled
   in Live, so the agent enrolls again on its first Live record.
3. Give the anchorer a log store. On a Live API key, the SDK refuses to sign a record
   without one.

Then build an evidence pack and check that it reads Verified and exits 0, with no Sandbox
line. See [Build and verify evidence](/guides/evidence).

### Why a Sandbox pack is never evidence

A simulated stamp is Sanning's own computation. It supplies no independent time, so no
reader can check it against anything outside Sanning. The console's record page says
so: "simulated stamp: sandbox, not evidence". The signed `environment` is inside the signed bytes, so
nobody can relabel a Sandbox record as a Live one without breaking its signature. The
kernel reads that value offline, prints a Sandbox line and exits 3 instead of 0. No flag
turns exit code 3 into 0.

Verification stays offline in both modes, and Sanning is never in the trust path in
either.

## Test in CI

This page puts a Sandbox anchor, a pack and a verify into a CI job. The job proves that
your integration still anchors and that your records still verify, without writing to the
public record.

### Use a Sandbox API key and one stored seed

Store two secrets in your CI system:

- `SANNING_API_KEY`: a Sandbox API key. Create it under **Settings, API keys** in the
  Sandbox. Do not put a Live API key in a test pipeline.
- `SANNING_SIGNING_SEED`: a signing seed you generate once, with the commands in the
  [Quickstart](/quickstart#make-a-signing-seed).

Load the same seed on every run. A new seed under an existing `agent_id` is read as an
unauthorized identity rotation, and a new `agent_id` on every run enrolls a new agent
each time. The Sandbox holds at most 25 active agents, so a job that mints a new agent
per run eventually fails with `SANDBOX_LIMIT_REACHED`. See
[Limits](/reference/errors#limits).

### Accept exit code 3

A Sandbox pack verifies, and `verify` exits 3 for it. A CI job that requires exit code 0
never passes, so assert 3 instead:

```bash
set +e
sanning-proof verify bundle.json --logs logs/
code=$?
set -e

if [ "$code" -ne 3 ]; then
  echo "expected exit code 3 (Sandbox), got $code"
  exit 1
fi
```

The check is strict on purpose. Exit 0 from a Sandbox pack would mean the records were
signed as Live, and exit 1 or 2 means a check failed or could not finish. All three are failures here.

### Wait for the stamp

A Sandbox stamp seals within about a minute. Until it does, `bundle` refuses with
exit 2 and writes nothing. Once the stamp has sealed, `bundle` exits 3 for a
Sandbox pack, the code `verify` gives it. Retry on 2 for a few minutes before you fail
the job:

```bash
for attempt in $(seq 1 12); do
  set +e
  sanning-anchor bundle \
    --agent claims-triage \
    --from "$(date -u +%F)" \
    --to "$(date -u +%F)" \
    --logs ./logstore \
    --out pack.zip
  code=$?
  set -e
  if [ "$code" -ne 2 ]; then
    break
  fi
  sleep 15
done

if [ "$code" -ne 3 ]; then
  echo "expected exit code 3 (Sandbox pack), got $code"
  exit 1
fi
```

`bundle` exits with the code `verify` would give the pack it wrote, and it writes
nothing when that pack would read Failed. See [CLI](/reference/cli#bundle).

The window names today in UTC. A job that runs across midnight UTC can miss records
anchored before it, so anchor and bundle in one job.

### Keep the Sandbox tidy

Sandbox data older than 30 days is deleted daily, and you rarely need to clear it. If a
suite fills the Sandbox, an owner or admin can reset it from **Settings, Sandbox**. A
Reset keeps your API keys and signing keys, so the stored secrets keep working. See
[Sandbox and Live](/reference/api-keys#sandbox-and-live).

The Sandbox allows 5 requests per second per organization. A parallel test run that
exceeds it gets `SANDBOX_LIMIT_REACHED` with status 429 and a `Retry-After` header.
