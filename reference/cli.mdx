Two commands, owned by two packages, and the split matters.

| Command | Package | Who runs it |
|---|---|---|
| `bundle` | `@sanning/anchor`, `sanning-anchor` | You, to hand evidence over |
| `verify` | `@sanning/proof`, `sanning-proof` | Whoever you hand it to |

**An auditor never needs the write SDK.** Verification lives in its own package with no
account and no key, and no network unless you choose to pass a gateway URL for the
optional online check (see below).

## bundle

Assemble the hand-over pack for one agent over one period. This section is linked as
`docs.sanning.io/reference/cli#bundle` from the console's **Evidence** page.

<CodeGroup>
```bash TypeScript
npx @sanning/anchor bundle \
  --agent claims-triage \
  --from 2026-09-01 \
  --to 2026-09-30 \
  --logs ./logstore \
  --out pack.zip
```

```bash Python
sanning-anchor bundle \
  --agent claims-triage \
  --from 2026-09-01 \
  --to 2026-09-30 \
  --logs ./logstore \
  --out pack.zip
```
</CodeGroup>

Same flags, same exit codes, same output in both languages. One shared fixture grades
them, and neither passes by agreeing with the other.

| Flag | Required | Meaning |
|---|---|---|
| `--agent` | Yes | The agent whose records to gather. Use the name you anchored under |
| `--from` | Yes | Start of the period |
| `--to` | Yes | End of the period. A date-only bound names a whole day and is included; an ISO instant is exclusive |
| `--logs` | In practice | Your store root: the local directory holding `content/` and `records/`, or `s3://bucket` or `s3://bucket/prefix` |
| `--out` | Yes | Where to write the zip |
| `--allow-unstamped` | No | Assemble even when records in the period are not yet stamped. Takes no value |
| `--case` | No | From 0.15.0. Select the records whose own `context.case_id` is this case, and declare the pack about it. See [Hand over and verify a case](/guides/handoff-case#bundle-one-pack-per-agent) |

<Note>
  `--logs` is optional to the parser and required in practice. The command reads your
  record objects to work out which events are this agent's, because a
  minimum-disclosure envelope does not carry that name.
</Note>

**Authentication** comes from `SANNING_API_KEY` in the environment. There is no flag for
it. The key needs `anchor:read`.

**A declaration needs `SANNING_SIGNING_SEED`.** Set it to the seed of the agent whose
records you are bundling, 64 lowercase hex characters, and `bundle` signs a declaration,
the pack's own statement of what it holds, and seals the pack with that key. Without it,
`bundle` seals the pack with a one-time key it mints and discards, and builds no
declaration. With it set, `bundle` refuses a window holding a record that names no case,
a window holding more than one case, and an `s3://` log store. See
[Hand over and verify a case](/guides/handoff-case#bundle-one-pack-per-agent).

**`--agent` is checked twice.** The records route the command reads from filters by this
name on the server, and the command also refuses if a record it gets back names a
different agent. A misspelled `--agent` prints `bundle: no stamped records for agent
"…" … (the control plane does not recognize this agent)` and exits 1, rather than
building an empty or mismatched pack.

**`bundle` refuses a window that mixes Sandbox and Live evidence** for one agent, because
a pack carries one mode.

**It verifies its own output before writing.** If the assembled pack does not verify,
nothing is written and the command exits non-zero. A pack that only fails at the auditor
is a pack shipped broken.

**From 0.16.0, `bundle` writes `witness-cache.json` beside `bundle.json`** when a stamp's
witness is already in a block. It records a witnessed time your side already looked up, so
a reader is not required to; `verify` and `case` print it labelled not checked unless you
pass `--gateways`, and a missing or partial cache never blocks the pack.

## Pack reporting

After `bundle` writes the pack, it reports that it did so to Sanning, using the same API
key, so the pack appears under **Evidence** in the console. The report carries your
agent's name, the environment, the window, the record count, the SHA-256 of `bundle.json`,
the SDK name and version, and the time the pack was built. It never carries the pack, a
log, a record id, or a file name, and Sanning never receives the pack itself.

Every run of `bundle` builds a new `bundle.json` with its own build time, so every run is
reported, even one covering a period you have already handed over.

If the report fails, `bundle` prints one line naming the pack's digest and still exits 0:
the pack was assembled and verified before the report was attempted, so a reporting
failure does not undo it. The credential needs `anchor:read`, the scope it already holds
to read your records back.

## verify

Check a pack. No account, no key, no relationship with Sanning.

```bash
npx @sanning/proof verify bundle.json --logs logs/
```

| Argument | Meaning |
|---|---|
| `bundle.json` | The bundle file, extracted from the pack |
| `--logs` | The folder of disclosed files, if the pack carries them. From 0.17.0, only regular files named `<event_id>.json` are read; links are never followed, subfolders are never entered, and every other entry is named. Exit 2 for a non-UTF-8 name, more than 50,000 entries, or more than 1 GiB of `<event_id>.json` files |
| `--gateways` | Comma-separated gateway URLs. Re-fetches each witness and byte-compares it |
| `--files` | From 0.14.0. Files beside the pack to match against the records that commit to their bytes: SHA-256 over each file, checked against `event.content_hash` or a hand-off file part's `content_hash`. Never matched by name. From 0.17.0 a path can be a folder: the regular files inside it are matched, recursively and hidden files included, and a link, a pipe, or an unreadable file is named in the `skipped` list (`files.skipped` in `--json`) |
| `--json` | Print the verdict, the causes and the exit code as JSON |

`verify`, `export` and `case` share one exit table:

| Exit | Means |
|---|---|
| 0 | Verified, or the export was written |
| 1 | A check ran and failed, or the pack deviates from its own declaration. The output names the record |
| 2 | The input could not be read |
| 3 | Undetermined: the pack reads `incomplete` or `partial`, or a gateway re-fetch was asked for and something in it could not be checked |
| 4 | Mixed: more than one outcome, none of them failed |
| 5 | Sandbox: every check passed, but the pack holds a record signed `environment: "dev"`, which is sandbox evidence, not production evidence. A pack whose records are all `dev` also exits 5 when the only witness left unchecked is a simulated one |

Exit 5 is the Sandbox: the pack verified, and its stamp is simulated. See
[Sandbox and live](/concepts/sandbox-and-live).

A pack whose declaration says a record's content is withheld on purpose reads
`verified`; a pack with no declaration and an undisclosed record reads
`incomplete` instead, because nothing says the absence was on purpose. Only an
`arweave` witness with a 43-character transaction id is re-fetched from a
gateway. A witness of any other kind, or an id that is not exactly 43
characters, is reported as not checked, and the run answers `partial` and
exits `3`.

**From 0.14.0, parsing is stricter.** A bundle, an envelope or a log file whose JSON
repeats a key reads `malformed`, exit 2, rather than silently keeping the last value.
`event_id`, `payload_hash`, `payload_ref` and `subject`, and every time field a verdict
carries, are checked against their exact wire shapes; a value that fails names the field
and reads `malformed` or `failed` where it used to read `verified` with nothing to compare
against. No item on the public record is affected.

`sanning-proof` on PyPI is the same kernel and ships the same `verify` command. See
[Verify at the command line](/verify/cli).

## case

Read one or more packs, or a case file, as one case, and print one verdict
with every exception named. Each argument is a pack folder, a folder holding
several packs, or a case file named `<name>.zip`:

```bash
npx @sanning/proof case assessor-pack/ reviewer-pack/
npx @sanning/proof case case-5d1e9a.zip
```

`case` shares `verify`'s exit table, above. `--gateways` takes a
comma-separated list and re-fetches each pack's witnesses, reported on their
own line; the lookup never moves the verdict. `--files`, from 0.14.0, works
the same way `verify` uses it: files handed in beside the case are matched
against every party's records, never by name, and a path can be a folder from
0.17.0. See
[Hand over and verify a case](/guides/handoff-case#read-the-case-at-the-command-line).

**From 0.17.0, `case` also matches the files that sit outside every pack, with no
flag.** Each regular file in the `.zip` or in the folder `unzip` makes of it is hashed
with SHA-256 and listed as vouched for by a record in a named pack, as matching no
record, or as skipped (a link, a pipe, a refused zip entry, or an unreadable file). The
section is information only: the verdict and exit code never move. The loose files
share 1 GiB, and a file past it is skipped as `too_large`. A `.zip` larger than
1.25 GiB on disk exits 2 before it is read. If a file the case index lists passes
its 1 GiB, the comparison reports `case_index_file_too_large`; if `contents.json`
would pass the run's whole-read budget, or cannot be read, the index reads as
`case_index_unreadable` and the verdict still prints.

## Getting help

`--help` works on the top-level command in both languages. On a subcommand it exits 2 with
`unknown argument: --help`, which is a rough edge rather than a failure.

```bash
sanning-anchor --help
npx @sanning/anchor --help
```
