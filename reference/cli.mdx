This page lists the commands, their flags and their exit codes. For the steps, see [Build an evidence pack](/evidence/build) and [Verify an evidence pack](/evidence/verify).

Three commands come from two packages, and each package has a TypeScript and a Python version.

| Command | Package | Who runs it |
|---|---|---|
| `bundle` | `@sanning/anchor` (TypeScript), `sanning-anchor` (Python) | You, to build an evidence pack |
| `verify` | `@sanning/proof` (TypeScript), `sanning-proof` (Python) | The reviewer, to check one pack |
| `case` | `@sanning/proof`, `sanning-proof` | The reviewer, to check the packs of one case together |

The reviewer never needs the write SDK. The verifier has its own package, and it needs no account, no API key and no network. The one exception is the optional lookup of stamps on the public record, which you turn on with `--gateways`.

In TypeScript, run the commands with `npx`, such as `npx @sanning/anchor bundle`. In Python, run `sanning-anchor bundle` and `sanning-proof verify`. The flags, the exit codes and the output are the same in both languages.

## Exit codes

`bundle`, `verify` and `case` share one table of exit codes.

| Exit | Name | Means |
|---|---|---|
| 0 | Verified | Every claim that applies is proven. |
| 1 | Failed | A claim is disproven. A Sandbox pack that fails also exits 1. |
| 2 | Incomplete | Nothing is disproven, and at least one claim could not be checked. A Sandbox pack that is incomplete also exits 2. |
| 3 | Sandbox | The pack is Verified, and a record was made with a Sandbox API key. It is not production evidence. |
| 4 | Could not run | A bad flag, a missing file, or an input that is not a pack or a case. |

No flag turns exit code 3 into 0.

## bundle

`bundle` builds an evidence pack from Sanning's records and your log store. It checks the pack the way `verify` does before it writes anything.

```bash
npx @sanning/anchor bundle \
  --agent claims-triage \
  --case case-4b19de \
  --logs ./logstore \
  --out case-4b19de.zip
```

Without `--case`, `bundle` builds a pack for one agent over a period:

```bash
npx @sanning/anchor bundle \
  --agent claims-triage \
  --from 2026-11-01 \
  --to 2026-11-04 \
  --logs ./logstore \
  --out claims-triage-2026-11-04.zip
```

| Flag | Required | Meaning |
|---|---|---|
| `--agent` | Yes | The agent whose records to gather, by the name it records under. Give it more than once, with `--case`, to write a case file. |
| `--case` | No | Select the records whose own signed case ID is this case, and declare the pack about it. A case pack takes no dates and holds every record of the case, however long it ran. |
| `--from` | Without `--case` | The start of the period: a whole UTC day, written `YYYY-MM-DD`. A time is refused. |
| `--to` | Without `--case` | The end of the period: a whole UTC day, written `YYYY-MM-DD`. That day is included. |
| `--logs` | In practice | The root of your log store: a local folder that holds `content/` and `records/`, or `s3://bucket` or `s3://bucket/prefix`. For a case file, give it once for every agent, or once for each `--agent` in the same order. |
| `--out` | Yes | Where to write the zip. A `.zip` ending is added if it is missing. |
| `--base-url` | No | The control plane to read from. The default is `https://api.sanning.io`, or the value of `SANNING_BASE_URL`. |
| `--allow-unstamped` | No | Build the pack even when records in the period are recorded and not stamped yet. Takes no value. |
| `--handoffs-only` | No | With `--case`, put only the case's hand-off records in the pack. Needs `SANNING_SIGNING_SEED`. |
| `--report-file` | No | For a case file, and it can be given more than once: put this file under `report/` in the case file. No record commits to it. |

`--logs` is optional to the parser and required in practice. The command reads your records from the log store to work out which of them belong to the agent, because a record that Sanning holds does not carry the agent's name.

### Environment variables

| Variable | Meaning |
|---|---|
| `SANNING_API_KEY` | Your API key. There is no flag for it, so that it stays out of your shell history. It needs the scope `anchor:read`. |
| `SANNING_SIGNING_SEED` | The seed of the agent in `--agent`, as 64 lowercase hex characters. With it, `bundle` signs a declaration, which is the pack's statement of which records it holds, and seals the pack with the agent's key. Without it, `bundle` seals the pack with a one-time key that it discards, and builds no declaration. |
| `SANNING_SIGNING_SEEDS` | For a case file: one seed for each agent, written `intake=SEED,review=SEED`. `SANNING_SIGNING_SEED` is refused beside it. |
| `SANNING_SIGNING_KEY_KIND` | Whose key the seed is: `agent` (the default) or `organization`. With `organization`, the pack's issuer is your organization, and not the agent. |
| `SANNING_S3_ENDPOINT`, `SANNING_S3_ACCESS_KEY_ID`, `SANNING_S3_SECRET_ACCESS_KEY` | Needed when `--logs` is an `s3://` URL. TypeScript also needs `@aws-sdk/client-s3`. Python needs the `s3` extra. |
| `SANNING_GATEWAY_URL` | A gateway to the public record. When it is set, `bundle` asks it for the block height and time of each stamp, and writes them to `witness-cache.json` beside `bundle.json`. A missing or partial cache never blocks a pack. |
| `SANNING_BASE_URL` | The control plane to read from, in place of the default. |

### What bundle does

- `--agent` is checked twice. The command filters by the name on the server, and it also refuses if a record that comes back names a different agent. A misspelled name stops with `the control plane does not recognize this agent`, and the command writes no pack.
- It refuses a period that mixes Sandbox and Live records for one agent, because a pack holds one environment.
- With several `--agent`, it builds one pack for each agent and writes them together as a case file, under `packs/<agent>/`, beside an unsigned `contents.json` and a `HOW-TO-VERIFY.txt`. Every agent must have a pack, or the command writes nothing.
- With `--from` and `--to`, and `--to` is today, the period ends at the end of the last sealed interval, so that every record in the pack has a stamp.
- The window is matched against the time that Sanning received each record, which can be a moment earlier than the time on your machine. A record recorded within a moment of 00:00 UTC can belong to the neighbouring day. Compare the pack's record count with what your agent recorded, and build the neighbouring day too when they differ.

### bundle exit codes

`bundle` exits with the code that `verify` would give the pack it wrote.

| Exit | Means |
|---|---|
| 0 | The pack was written, and it reads Verified. |
| 1 | Nothing was written, because the pack would read Failed. |
| 2 | The pack was written and reads Incomplete, for example because a stamp is not on the public record yet. Or nothing was written because records are not stamped yet, or Sanning could not be reached. Run `bundle` again later. |
| 3 | The pack was written and reads Verified with Sandbox records. |
| 4 | Nothing was written, because the command could not run: a bad flag, an input it cannot read, no records that match, a case that Sanning did not read whole, or an output it cannot write. |

### Pack reporting

After `bundle` writes a pack, it tells Sanning that it did, with the same API key. The report holds the agent's name, the environment, the period, the record count, the SHA-256 of `bundle.json`, the SDK name and version, and the time the pack was built. It never holds the pack, a log, a record ID or a file name. You find it under **Evidence** in the console. Every run builds a new `bundle.json`, so every run is reported.

If the report fails, `bundle` prints one line with the pack's digest and still exits with the pack's code.

## verify

`verify` checks one pack. It needs no account and no API key.

```bash
npx @sanning/proof verify bundle.json --logs logs/
```

| Argument | Meaning |
|---|---|
| `bundle.json` | The bundle file from the unzipped pack. |
| `--logs` | The folder of content that the pack carries. The command reads only regular files named `<event_id>.json`. It never follows a link or enters a subfolder, and it names every other entry. It exits with code 4 for a name that is not UTF-8, for more than 50,000 entries, or for more than 1 GiB of content. |
| `--gateways` | Gateway URLs to the public record, separated by commas. The command fetches each stamp from them and compares its bytes. |
| `--files` | Files that you hold beside the pack. The command hashes each one and matches it, by SHA-256 alone, against what the pack's records commit to. A path can be a folder: the command matches the regular files inside it, found recursively. It never matches by name, and the verdict never moves. |
| `--json` | Print the report as JSON, for a script. See [JSON output](#json-output). |

The command parses strictly. A bundle, an envelope or a log file whose JSON repeats a key exits with code 4. A value that is not in its exact wire shape reads Failed, and the report names the field.

### Text output

The text report starts with the verdict, then prints only the lines that apply:

```text
<verdict>
<one line for each claim that is disproven or not proven>
Next: <one next action>
Note: <one line for each note>
Sandbox: these records are sandbox records, not production evidence.
Witness: <the witness line>
```

The verdict is one of `Verified`, `Failed: do not rely on this evidence.`, `Failed: a record does not follow the rules.` and `Incomplete: not everything could be checked.` The `Witness:` line is `Confirmed on the public record`, `Not checked` or `The public record holds different bytes`. Only a lookup that finds other bytes changes the verdict. A gateway that cannot be reached moves nothing, and the line says so.

After these lines comes a blank line and the detail for each record.

### JSON output

`--json` carries the same words as data, so a script can print the report from the JSON alone.

| Member | Holds |
|---|---|
| `verdict` | `{status, reason_kind}`. `status` is `verified`, `failed` or `incomplete`. `reason_kind` is `changed` or `nonconforming`, and it appears on `failed` only. |
| `claims` | One entry for each of the six claims: `claim`, `label`, `question`, `state` (`proven`, `disproven`, `not_proven` or `not_in_scope`), `reason` on `not_proven` and `not_in_scope`, `items` (the records the claim is about, by `event_id`) and `problems`. |
| `person` | The words of the text report, as data: `title`, `title_parts`, `lines`, `line_parts`, `next`, `notes`, `note_parts`, `sandbox`, `witness` and `witness_state`. |
| `exit_code` | The exit code. |

## case

`case` reads one or more packs, or a case file, as one case. It prints one verdict, and it names every exception. Each argument is a pack folder, a folder that holds several packs, or a case file named `<name>.zip`.

```bash
npx @sanning/proof case case-4b19de.zip
npx @sanning/proof case intake-pack/ review-pack/
```

`case` uses the same exit codes. A case reads as its worst pack. `--gateways`, `--files` and `--json` work as they do for `verify`, and `case --json` carries the same `verdict`, `claims`, `person` and `exit_code` members.

`case` also matches every file in the zip, or in the folder that unzipping it makes, that sits outside every pack. It hashes each file with SHA-256 and lists it as vouched for by a record in a named pack, as matching no record, or as skipped. This section is information only: the verdict and the exit code never move.

## Getting help

`--help` works on each command and exits with code 0 in both languages.

```bash
npx @sanning/anchor --help
npx @sanning/proof --help
sanning-anchor --help
sanning-proof --help
```
