---
title: "Scopes"
description: "What each scope allows, and the one combination that fails late"
---

An API key authenticates your organization. It is not the key that signs your evidence.

| Scope | Allows |
|---|---|
| `agent:enroll` | Enroll a signing key against an agent name |
| `anchor:write` | Anchor records |
| `anchor:read` | Read your own records back, which is how a pack is built and how `bundle` reports one |
| `verify:submit` | Submit a record to a verify endpoint |
| `verify:read` | Read back a verify verdict |

In the console, **Create key** asks for a name and whether the key can
**Verify**. Every key gets `agent:enroll`, `anchor:write` and `anchor:read`
under **Anchor**; checking **Verify** adds `verify:submit` and `verify:read`.
An agent runtime never needs the verify pair.

## The combination that fails late

<Warning>
  A key with `anchor:write` alone anchors correctly, possibly for weeks, and then fails
  the first time you build a pack.
</Warning>

Building a pack reads your own records back, so it needs `anchor:read`. Nothing surfaces
the gap until then, because anchoring never touches the read routes.

Mint keys for a runtime with all three:

```
anchor:write  anchor:read  agent:enroll
```

## Why a runtime needs agent:enroll

Both SDKs enroll the signing key before the first anchor, so the agent appears on your
fleet with no enrollment step written by you. The enrollment happens **in the runtime**,
which is where the signing key is, so the runtime's credential must be allowed to do it.

## What the signing key does, and what it never leaves

The API key and the signing key are different things and the split is the security model.

| | Held by | Reaches Sanning |
|---|---|---|
| API key | Your organization | Yes, as a bearer credential |
| Signing key | Your agent | Never |

Sanning cannot produce a record that verifies as yours, because it has never held the key
that signs one.
