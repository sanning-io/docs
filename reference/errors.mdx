---


Sanning's errors fall into three groups, and telling them apart saves the most time.

- **Not yet.** The plane is settling. Wait and retry.
- **Wrong shape.** Your call or your key is wrong. Change something and retry.
- **Refused.** Sanning is declining on purpose. Read the reason.

## Not yet

These resolve on their own. Retry rather than debugging.

<AccordionGroup>
  <Accordion title="no stamped records for agent claims-triage in ...">
    The interval containing your records has not been sealed and published yet. It means
    *not yet*, never *you have no evidence*. If records in the window are anchored and
    waiting for a stamp, a second line names how many.

    Wait for the interval to close and run the command again. See
    [Wait for the stamp](/guides/evidence#wait-for-the-stamp).
  </Accordion>
  <Accordion title="N record(s) in ... are anchored and retained but not yet stamped">
    Some records in the period are stamped and some are not, so a pack built now would
    leave the unstamped ones out. Nothing inside a pack records what it omitted, so the
    recipient could not tell it was short for the period it names. The verb refuses
    instead.

    Wait for the interval covering them to seal and run the command again. To hand over
    the stamped records anyway, pass `--allow-unstamped`, and say in the cover note how
    many were left out. See [Wait for the stamp](/guides/evidence#wait-for-the-stamp).
  </Accordion>
  <Accordion title="the envelope route returned no envelope">
    A record anchored seconds ago is not readable through the read routes yet. Placement
    settles after the write returns.

    Wait and retry. Building a pack immediately after a run races your own newest record.
  </Accordion>
</AccordionGroup>

## Wrong shape

<AccordionGroup>
  <Accordion title="SCOPE_NOT_ALLOWED, required: anchor:read">
    Two different refusals produce this line, and the response body tells them apart.

    If it carries a sentence naming an address to write to, this is not a key you built
    wrong: every key you create already carries `anchor:read`, so the refusal means your
    organization is not enabled for that route. Your records are intact and anchored;
    the credential cannot read them back.

    If it carries no sentence, only `required` and the key's own `keyScopes`, the key
    itself genuinely lacks the scope. This is the case for a key an operator minted
    through `POST /api/v1/admin/keys`, which is not bound to the two-scope-set rule
    `POST /api/v1/user/keys` enforces. Check what the key was minted with.

    See [API keys and signing keys](/reference/api-keys).
  </Accordion>
  <Accordion title="--logs was not given, so this verb cannot read your log store">
    `--logs` is required in practice. The command reads your record objects to work out
    which events belong to this agent, because a minimum-disclosure envelope does not
    carry that name.

    Point it at your store root, the directory holding `content/` and `records/`.
  </Accordion>
  <Accordion title="reading an s3:// log store needs SANNING_S3_ENDPOINT, ...">
    `--logs` accepts an `s3://` URL, and reading one needs `SANNING_S3_ENDPOINT`,
    `SANNING_S3_ACCESS_KEY_ID` and `SANNING_S3_SECRET_ACCESS_KEY` in the environment.
    The message names the ones that are missing.

    There is no flag for them: a credential in argv lands in shell history. See
    [Keep the content](/guides/evidence#keep-the-content).
  </Accordion>
  <Accordion title="bundle: missing required flag(s): --from, --to">
    The pack covers a period and you must name it. `--agent`, `--from`, `--to` and `--out`
    are all required.

    Each bound is a whole UTC day, written `YYYY-MM-DD`. A full timestamp such as
    `2026-09-01T09:00:00Z` is refused, exit 4.
  </Accordion>
  <Accordion title="N record(s) in ... have no record object in your log store">
    The window you asked for includes records whose bytes are not in the store you pointed
    at. Usually the window is wider than you meant.

    The command refuses rather than quietly dropping them, because a pack that silently
    omits records an auditor asked for is worse than no pack.
  </Accordion>
  <Accordion title="the control plane does not recognize this agent">
    The plane's records route filters by `--agent` on the server, so a name that does not
    match one of your organization's agents stops there before `bundle` reads anything back. The
    command prints `bundle: no stamped records for agent "…"` with this reason, and exits 4.

    Check the spelling against the console's **Agents** page. `--agent` takes the name you
    anchored under, not a display name you renamed it to later.
  </Accordion>
  <Accordion title="N record(s) ... carry no context.case_id">
    From 0.15.0. `bundle --case` with `SANNING_SIGNING_SEED` set found records in the
    window that name no case, so it cannot tell whether they belong to the case it is
    declaring.

    Pass the case id on every record in the case when you anchor it (`caseId` in
    TypeScript, `case_id` in Python), then run `bundle` again. See
    [Give each piece of work a case id](/guides/langchain#give-each-piece-of-work-a-case-id).
  </Accordion>
  <Accordion title="this pack would declare itself about case ..., and N selected record(s) name N other case(s)">
    From 0.15.0. `bundle` without `--case`, with `SANNING_SIGNING_SEED` set, found
    records that name a case. A declared pack names one case, so it refuses rather than
    put those records under the agent's name.

    Pass `--case` and run the command once per case.
  </Accordion>
  <Accordion title="cannot read --logs logs/">
    The pack has no `logs/` directory. A pack of hand-off records has none, because no
    hand-off record discloses content. Run `verify` without `--logs`.
  </Accordion>
  <Accordion title="pack.zip is not valid JSON: Unexpected token 'P'">
    You handed the kernel a zip. `PK` is the archive's own signature.

    Extract it and point at `bundle.json` inside. See
    [Verify an evidence pack](/guides/evidence#verify-an-evidence-pack).
  </Accordion>
</AccordionGroup>

## Refused

<AccordionGroup>
  <Accordion title="the signing key is not enrolled in this organization">
    The plane accepts records only from keys the organization knows, so that every record
    has an identity behind it.

    Both SDKs enroll automatically before the first anchor. If you see this, the signing
    key reaching the plane is not the one that enrolled. The message names the two calls
    that enroll a key by hand, if you drive enrollment yourself.
  </Accordion>
  <Accordion title="AGENT_LABEL_REVOKED">
    That agent name was revoked. Revoking is deliberate and a revoked name cannot be
    re-enrolled by anyone, including whoever holds the old key.

    Recovering keeps the lineage: an owner or admin pins a new key for the name from
    **Settings, Signing keys** in the console, then the agent completes the re-key by
    restarting with that key. See
    [Re-key a revoked name](/reference/api-keys#re-key-a-revoked-name).
  </Accordion>
  <Accordion title="AGENT_ID_KEY_MISMATCH">
    Your API key is bound to a different `agent_id` than the one in the request, and a key
    bound to one agent 403s for every other one.

    A key you create in the console is never bound to an agent, so this appears only on a
    key Sanning bound for you. Use an ordinary key from **Settings, API keys**, which
    covers all of your agents.
  </Accordion>
  <Accordion title="AGENT_CHALLENGE_INVALID">
    The proof-of-possession challenge is missing, expired, already used, or was not
    issued for this agent. Request a fresh challenge and sign it straight away.
  </Accordion>
  <Accordion title="AGENT_POP_FAILED">
    Proof-of-possession failed: the signature does not verify against the public key the
    challenge names. Check that the signer holds the key you believe it holds.
  </Accordion>
  <Accordion title="AGENT_ROTATION_UNAUTHORIZED">
    This agent already has an active signing key, and rotating it needs
    `previous_signature`, the same challenge signed by the outgoing key. If that key is
    lost, an owner or admin recovers the agent by pinning a new key from **Settings,
    Signing keys**, which the agent then claims by restarting with it.
  </Accordion>
  <Accordion title="AGENT_REKEY_REQUIRED">
    The signature verifies, but this agent has no active signing key left to rotate: its
    only live key is still draining from an earlier rotation. The SDK will not rotate off
    a draining key, so an owner or admin pins a new key for the agent from **Settings,
    Signing keys** instead, and the agent claims it on its next restart.
  </Accordion>
  <Accordion title="SIGNING_KEY_ALREADY_ENROLLED">
    This public key is already enrolled somewhere in Sanning, under this name or
    another, in your organization or a different one, whether active, retired or
    revoked. A signing key is unique across every organization, not only your own, and
    cannot be reused for a different agent or as a rotation back onto an earlier key.
    A key revoked in *your own* organization answers with the more specific
    `SIGNING_KEY_PREVIOUSLY_REVOKED` instead. The message names no other organization.
    Generate a new key where the agent runs and enroll that one instead. Nothing was
    changed.
  </Accordion>
  <Accordion title="SIGNING_KEY_PREVIOUSLY_REVOKED">
    This public key was revoked in your organization, so it cannot be enrolled again
    under any name there. Revoking a key repudiates it at every time, whichever name
    held it. A key revoked in a different organization is refused too, as
    `SIGNING_KEY_ALREADY_ENROLLED`, and so is a key belonging to an organization
    deleted since. Generate a new key where the agent runs and enroll that one
    instead. Nothing was changed.
  </Accordion>
  <Accordion title="SIGNING_KEY_NOT_REVOKED">
    A console re-key was asked for a name that is not revoked: one of its keys is still
    active, or the name has already been re-keyed. Rotate a live key through the SDK
    instead, which asks the outgoing key to counter-sign. Nothing was changed.
  </Accordion>
  <Accordion title="no-log-store and local-log-store">
    Live refuses an envelope that does not say where its bytes are kept. `no-log-store`
    (400) means the envelope names no log store. `local-log-store` (400) means its locator
    is a `file:` path, which is one machine's disk and not a retained store. The Sandbox
    does not check either.

    Configure a log store, and do not pass a `file:` `payloadRef`. For Live, keep the
    store in S3-compatible storage. See
    [Keep the content](/guides/evidence#keep-the-content) and [Quickstart](/quickstart).
  </Accordion>
  <Accordion title="a store failure means no anchor">
    The SDK writes your bytes to your log store before anchoring, and a store failure
    stops the anchor. There is no best-effort mode on this path.

    Anchoring a commitment to bytes you cannot produce is the one state that cannot be
    repaired afterwards. See [Keep the content](/guides/evidence#keep-the-content).
  </Accordion>
</AccordionGroup>

## Sandbox errors

These appear when an API key reaches the wrong mode, or when you hit a Sandbox ceiling.
They are separate from the three groups because the fix is about modes, not about the
call. See [Sandbox and Live](/reference/api-keys#sandbox-and-live).

<AccordionGroup>
  <Accordion title="SANDBOX_KEY_ON_LIVE (401)">
    You sent a Sandbox API key to a Live plane. Live accepts only Live API keys, and the
    message names the prefix it accepts. Nothing was read.

    Use a Live API key, or check that your base URL is `https://api.sanning.io`.
  </Accordion>
  <Accordion title="LIVE_KEY_ON_SANDBOX (401)">
    You sent a Live API key to a Sandbox. The Sandbox accepts only Sandbox API keys, and
    the message names the prefix it accepts. Nothing was read.

    Use a Sandbox API key. Create one under **Settings, API keys** after you
    **Switch to sandbox** in the console.
  </Accordion>
  <Accordion title="ENVIRONMENT_MODE_MISMATCH (400)">
    The record you signed names an environment the Sandbox does not accept. The Sandbox
    accepts `dev` and nothing else, and it refuses `production` and a record with no
    environment. Nothing was recorded.

    With a Sandbox API key, leave out the `environment` argument and the SDK signs the
    right value. If you sign with your own submitter, sign `dev`.
  </Accordion>
  <Accordion title="SANDBOX_LIMIT_REACHED (403 or 429)">
    You reached a fixed Sandbox ceiling. `details.limit` names it and `details.value`
    states its number. A 403 does not clear by waiting. A 429 carries `Retry-After`.

    For a ceiling that a Reset frees, `details.reset` points at **Settings, Sandbox,
    Reset the sandbox**. For `keys`, revoke an API key instead, because a Reset keeps
    API keys. Every ceiling and its fix is in
    [Limits](/reference/errors#limits).
  </Accordion>
  <Accordion title="EMAIL_NOT_VERIFIED (403)">
    Live enters the Sandbox only for a member whose email address is verified.

    Verify your email address, then select **Switch to sandbox** again.
  </Accordion>
  <Accordion title="SANDBOX_ENTRY_REFUSED (401)">
    The Sandbox refused the credential Live issued for your entry, and no session was
    issued. `details.reason` names the check that failed, such as `expired`, `replayed`
    or `org-deleted`.

    Select **Switch to sandbox** again from the Live console.
  </Accordion>
</AccordionGroup>

## Verdicts are not errors

`incomplete` is an answer, not a failure. A check that could not run is reported as not
proven, and the kernel exits 2, not 1. See [Read the result](/guides/evidence#read-the-result).

## Limits

Each mode limits how fast you can call and how much you can hold. The Sandbox has fixed
numbers, the same for every organization. Live limits follow your plan.

### Sandbox ceilings

Every Sandbox organization gets these numbers, whatever plan it holds in Live. They are
not settings: nobody can raise one for you.

| `details.limit` | Ceiling | Status | What clears it |
|---|---|---|---|
| `rate` | 5 requests per second, and 300 per minute, per organization | 429 | Wait for `Retry-After` |
| `keys` | 10 active API keys | 403 | Revoke a key. A Reset keeps API keys |
| `agents` | 25 active agents | 403 | Reset the sandbox, which decommissions every agent |
| `records` | 10,000 records held | 403 | Reset the sandbox |
| `bytes` | 500 MB of stored envelopes held (500,000,000 bytes) | 403 | Reset the sandbox |
| `reset` | One Reset every 5 minutes per organization | 429 | Wait for `Retry-After` |
| `deployment` | 50 GB of stored envelopes across every Sandbox organization together (50,000,000,000 bytes) | 403 | Reset the sandbox, which frees your share |

Every refusal is the error `SANDBOX_LIMIT_REACHED`. `details.limit` names the ceiling and
`details.value` states its number. The 429 refusals carry a `Retry-After` header in
seconds. The 403 refusals do not clear by waiting, so repeating the request cannot
succeed until you free something.

Where a Reset frees the ceiling, `details.reset` names the route and the console path:
**Settings, Sandbox, Reset the sandbox**. See [Errors](/reference/errors#sandbox-errors).

A resend of a record the organization already holds is never refused for `records`,
`bytes` or `deployment`: it stores nothing new.

The Sandbox has no monthly quota and no overage, and is never billed.

### Live limits

Live limits come from your plan: the request rate, the number of API keys and agents, and
the monthly usage allowances. A request over the rate limit answers 429
`RATE_LIMIT_EXCEEDED`. A request over a monthly allowance that your plan caps answers 429
`QUOTA_EXCEEDED`. Ask the Sanning team for the numbers on your plan.

Live has no purge and no Reset, so the `records`, `bytes` and `deployment` ceilings
exist only in the Sandbox.
