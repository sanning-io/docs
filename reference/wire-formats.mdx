The record formats are specified in the open, in the
[`sanning-io/specs`](https://github.com/sanning-io/specs) repository. Those documents are
normative. This page tells you which one answers which question.

## Which one answers what

| Specification | Answers |
|---|---|
| [`specs/agent-events.md`](https://github.com/sanning-io/specs/blob/main/specs/agent-events.md) | The `sanning.agent/1` vocabulary: the 19 record types, every field, what each commits to by hash, what Sanning receives in each data mode, how hand-offs pair, and how a verifier reads one record |
| [`specs/events.md`](https://github.com/sanning-io/specs/blob/main/specs/events.md) | The `sanning.events/v2` profile: the signed envelope, the event record and its sections, chains, the record salt and the interval stamp |

The format of an evidence pack, how a holder obtains an inclusion proof, and the verdicts
over a pack are specified in a later release. Until then, the kernel in `@sanning/proof`
and `sanning-proof` is the reference for them, and
[What a verdict means](/verify/what-a-verdict-means) gives the plain reading.

A record signed `environment: "dev"` is Sandbox evidence: the kernel reports a pack that
holds one as Sandbox, with exit code 3. See [Sandbox and live](/concepts/sandbox-and-live).

## The parts worth reading first

**`events.md` section 2** requires a reader to ignore an optional envelope member it does not
know. That rule keeps every record verifiable as the format grows.

**`agent-events.md` section 10** says how a verifier reads one record: each check, the
verdict it gives and the reason. If you are deciding how much weight to put on a
`verified` result, read that section rather than this site's summary of it.
